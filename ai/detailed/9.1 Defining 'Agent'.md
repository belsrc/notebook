## Why this question matters

"Agent" is one of the most overloaded words in modern AI. The same word gets used by a robotics researcher, a multi-agent systems theorist, an LLM application engineer, and a marketing copywriter, and each of them means something different by it. Before we can design or evaluate agents, we need a definition precise enough to drive engineering decisions.

## The classical definition: perception and action

The standard textbook in artificial intelligence, Russell and Norvig's *Artificial Intelligence: A Modern Approach* (Russell & Norvig, 2020), defines an agent this way:

> "An agent is anything that can be viewed as perceiving its environment through sensors and acting upon that environment through actuators."

That definition produces the canonical perception-action loop, sometimes called the sense-think-act loop. It originates in mid-20th-century cybernetics (Wiener, 1948):

```
        ┌─────────────────────────┐
        │      ENVIRONMENT        │
        │  (the world, its state) │
        └─────────────────────────┘
              ▲            │
              │            │  percepts
     actions  │            │  (observations)
              │            ▼
        ┌─────────────────────────┐
        │         AGENT           │
        │   (decision function)   │
        └─────────────────────────┘
```

Formally, an agent is a function $f: P^* \to A$ where $P$ is the set of possible percepts and $A$ is the set of possible actions. The agent function maps *percept histories* (everything it has ever observed) to a chosen action. The history matters because two agents in the same momentary situation might choose differently based on what came before.

Russell and Norvig also give us the PEAS framework for specifying an agent's task environment:

- *P* (Performance) - How is "good behavior" measured?
- *E* (Environment) - Where does the agent operate?
- *A* (Actuators) - What can it do?
- *S* (Sensors) - What can it observe?

Concrete instances:

| Agent            | P (Perf.)          | E (Enviro.)   | A (Actuators)                  | S (Sensors)                |
| ---------------- | ------------------ | ------------- | ------------------------------ | -------------------------- |
| Thermostat       | Temp near setpoint | Room          | Heater relay                   | Thermometer                |
| Roomba           | Floor cleanliness  | Living room   | Wheels, brush                  | Bump, cliff                |
| Chess engine     | Win the game       | Chess board   | Move output                    | Board state                |
| Self-driving car | Safe, fast arrival | Public roads  | Steer, throttle, brake         | Camera, lidar              |
| LLM coding agent | Tests pass         | Codebase + OS | Edit files, run shell commands | Read files, command output |

This classical definition is deliberately broad. It accommodates everything from thermostats to humans. That breadth is a feature in academic AI but a bug for our purposes; it gives us no leverage to tell a chatbot apart from a self-improving system. We need to refine.

## Properties of "intelligent" agents

Wooldridge and Jennings, in their foundational survey "Intelligent Agents: Theory and Practice" (Wooldridge & Jennings, 1995), split the term into two notions.

The *weak notion* of agency requires four properties. Autonomy means operating without continuous direct human intervention and with some control over the agent's own internal state. Social ability means interacting with other agents and possibly humans. Reactivity means perceiving the environment and responding to changes in it. Pro-activeness means exhibiting goal-directed behavior and taking initiative rather than only reacting to stimuli.

The *strong notion* adds mentalistic attributes formalized in the BDI (Belief-Desire-Intention) architecture. Beliefs are the agent's model of the world. Desires are the goal states it wants to bring about. Intentions are its commitments to specific plans of action.

Franklin and Graesser, in "Is It an Agent, or Just a Program?: A Taxonomy for Autonomous Agents" (Franklin & Graesser, 1996), surveyed the literature and concluded that the term was *already* hopelessly ambiguous in 1996. They catalogued properties variously attributed to agents: reactive, autonomous, goal-oriented, temporally continuous, communicative, learning, mobile, flexible, and character-bearing. Their own proposed definition:

> "An autonomous agent is a system situated within and a part of an environment that senses that environment and acts on it, over time, in pursuit of its own agenda and so as to effect what it senses in the future."

The key additions over Russell-Norvig are *temporally continuous* (the agent persists over time) and *pursues its own agenda* (it has goals). These two additions exclude reflex programs like thermostats from "real" agency.

This history matters because every recent definition of "agent" is, knowingly or not, picking a subset of these properties.

## The LLM-era reframing

The term "agent" came roaring back into popular use when LLMs gained the ability to call external tools. The most-cited academic source is the ReAct paper (Yao et al., 2022), which introduced a prompting pattern in which an LLM interleaves Reasoning traces with Actions (tool calls), then feeds the results back into its context on the next step.

The modern LLM agent loop looks like this:

```
   ┌─────────────────────────────────────────────────────────┐
   │                                                         │
   │   ┌──────────────────┐                                  │
   │   │       LLM        │                                  │
   │   │   (reasons,      │                                  │
   │   │   decides next   │                                  │
   │   │   action)        │                                  │
   │   └────────┬─────────┘                                  │
   │            │                                            │
   │            │ tool call (action)                         │
   │            ▼                                            │
   │   ┌──────────────────┐                                  │
   │   │  Tool execution  │  ◄─── External world             │
   │   │  (files, APIs,   │       (filesystem, web,          │
   │   │  code, etc.)     │        databases, etc.)          │
   │   └────────┬─────────┘                                  │
   │            │                                            │
   │            │ result (observation)                       │
   │            ▼                                            │
   │   ┌──────────────────┐                                  │
   │   │     Context      │                                  │
   │   │  (running message│ ──┐                              │
   │   │   history)       │   │                              │
   │   └────────┬─────────┘   │                              │
   │            │             │ feed back                    │
   │            └─────────────┘ until LLM decides to stop    │
   │                                                         │
   └─────────────────────────────────────────────────────────┘
```

The structure is straightforward to describe in words. The system maintains a growing buffer of messages, which is the running conversation that accumulates the engineer's initial prompt, the LLM's reasoning and tool requests, and the outputs returned by those tools. On each iteration, the entire buffer is sent to the LLM. The LLM produces a response that may contain reasoning text, zero or more tool calls, or both. If it produces tool calls, the runtime executes each one, appends the result to the message buffer as a new "tool" message, and loops back to call the LLM again with the now-larger buffer. If it produces no tool calls, the loop terminates and the final response is returned. A defensive upper bound on the number of iterations is enforced to prevent runaway behavior.

Three structural properties of that arrangement deserve careful attention, because they are what make the system *behave* like an agent rather than a script.

First, the LLM decides when to stop. In a conventional program, control flow is determined by `if`, `for`, and `return` statements written by the engineer. In an agent loop, the engineer writes a loop, but the LLM chooses to exit it by emitting a response with no tool calls. Termination is delegated to the model. No condition in the runtime says "the task is finished"; only the model's judgment that it has nothing more to do can end the loop.

Second, the loop is bounded by a maximum step count. This is defensive engineering, what we will later call "negative space programming." Without a cap, a confused, looping, or adversarially-prompted LLM can iterate indefinitely, burning tokens, time, and money and potentially executing many unintended actions. The cap is the engineer reasserting partial control over a process that has otherwise been handed to the model. It is the single most important safety primitive in an agent runtime.

Third, observations are appended to the same context. The LLM sees its own prior reasoning, its prior actions, and the results of those actions, all in one growing transcript. This is what allows it to course-correct. It can read the output of a `read_file` call, notice that the file did not contain what it expected, and try a different file on the next step. "Memory," at this minimal level, is nothing more than "every message accumulated so far." More sophisticated memory schemes (summarization, retrieval, scratchpads) build on this primitive by selectively pruning or enriching that transcript, but the kernel is always the same.

These three properties are the core structural features that make an LLM loop an *agent* and not a *chatbot* or a *pipeline*: the model controls termination, the engineer enforces bounds, and the context accumulates everything that has happened so far.

## Anthropic's framing: workflows vs. agents

In December 2024, Anthropic published an engineering post titled "Building effective agents" (Schluntz & Zhang, 2024). It introduces a distinction that has become widely cited in industry, and it is the framing we will adopt for the rest of the course.

Anthropic uses the umbrella term *agentic systems* for any system built around LLMs that take actions. They then split this umbrella into two categories distinguished by who controls the control flow:

> "Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents, on the other hand, are systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish their tasks." (Schluntz & Zhang, 2024)

In other words:

- Workflow: Control flow is fixed by the engineer at design time. The LLM is called inside specific, predetermined slots.
- Agent: Control flow is decided by the LLM at runtime. The LLM chooses, each step, what to do next.

The spectrum from least-to-most agentic looks like this:

```
   More predictable                          More flexible
   More cost-efficient                       More capable
   Lower variance                            Higher variance
   Easier to evaluate                        Harder to evaluate
   ◄═══════════════════════════════════════════════════════════════►

   ┌───────────┐ ┌───────┐ ┌────────┐ ┌─────────────┐ ┌────────────┐
   │  Single   │ │ Chain │ │ Router │ │ Orchestrator│ │   Agent    │
   │  LLM call │ │       │ │        │ │  + workers  │ │   loop     │
   └───────────┘ └───────┘ └────────┘ └─────────────┘ └────────────┘
        │           │          │             │              │
        │           │          │             │              │
    No control    Fixed      Fixed         Fixed          Variable
    flow at      sequence,   branching,   decomposition,  control flow,
    all          engineer-   engineer-    engineer wrote   LLM decides
                 authored    authored     the dispatch    every step
                             classifier

   ◄──────────── WORKFLOWS ────────────►  ◄───────── AGENTS ──────────►
        (engineer-controlled flow)            (LLM-controlled flow)
```

The five workflow patterns Anthropic catalogues are worth knowing by name (Schluntz & Zhang, 2024).

*Prompt chaining* decomposes a task into a fixed sequence of LLM calls, each consuming the previous one's output. A classic example is outline, then draft, then polish.

*Routing* classifies the input with one LLM call and dispatches to a specialized handler. A support ticket might be classified as billing, technical, or account, then sent to the matching prompt.

*Parallelization* runs multiple LLM calls at the same time and aggregates the results. There are two flavors. In sectioning, a task is split into independent subtasks. In voting, the same query is run multiple times and the answers are combined.

*Orchestrator-workers* uses a central LLM that dynamically decomposes a task and dispatches subtasks to worker LLMs. This sits on the agentic edge of the workflow zone, since the decomposition is dynamic, though the worker invocation pattern itself is still engineer-defined.

*Evaluator-optimizer* pairs one LLM that produces output with another LLM that critiques it. The first then revises. The loop is bounded and the roles are fixed.

Distinct from all five, you have the *agent* itself: an LLM in a loop with tools, choosing each step what to do until it judges the task complete.

The point of the distinction is not to declare agents superior. The point is to make a clear engineering trade-off visible:

| Workflows                          | Agents                              |
| ---------------------------------- | ----------------------------------- |
| + Predictable cost                 | - Variable, often high cost         |
| + Predictable latency              | - Variable latency                  |
| + Easier to debug (read the code)  | - Harder to debug (trace decisions) |
| + Easier to evaluate (per-step)    | - Harder to evaluate (end-to-end)   |
| + Provably correct for fixed tasks | - Probabilistic correctness         |
| - Brittle for novel tasks          | + Adapts to novel situations        |
| - Engineer must anticipate paths   | + LLM discovers paths at runtime    |
| - Hard to extend                   | + Extends naturally with new tools  |

Anthropic's prescription, paraphrased: use the simplest pattern that solves your problem. Most things called "agents" in the wild are actually solved better by workflows. Reach for an agent only when the task genuinely requires open-ended decision-making that you cannot enumerate ahead of time.

## Why the word is contested

We can now see why people argue about "agent." They are not really disagreeing on facts. They are using different definitions, and the definitions emphasize different properties. The disagreement maps onto a set of axes:

| Axis              | Range of Positions                                            |
| ----------------- | ------------------------------------------------------------- |
| Tool use          | "Any LLM with tools" vs. "Must use tools autonomously"        |
| Control of flow   | "Engineer-wired" vs. "LLM-directed"                           |
| Autonomy          | "Confirms each step" vs. "Runs unattended"                    |
| Goal-directedness | "Responds to prompt"  vs.  "Pursues a long-running objective" |
| Memory            | "Stateless" vs. "Persistent across sessions"                  |
| Environment       | "Text in, text out" vs. "Embodied in world"                   |
| Population        | "Single agent" vs. "Multi-agent system"                       |
| Mentalistic state | "No internal state" vs. "BDI: beliefs, desires, intentions"   |

The major camps you will encounter:

1. The "everything is an agent" camp (marketing). Any LLM application is rebranded as an agent. Useful for press releases, useless for engineering decisions.

2. The "ReAct loop" camp (early LangChain, common engineering usage). An agent is an LLM looping with tools and reasoning steps. This is the most common operational definition in industry today.

3. The "Anthropic distinction" camp (this course). An agent is a system in which the LLM dynamically controls its own control flow with tools. Workflows are something else, often preferable.

4. The "classical AI" camp (Russell-Norvig disciples). Anything with sensors and actuators is an agent, thermostats included. Too broad for engineering decisions, though correct historically.

5. The "BDI / strong agency" camp (academic AI, philosophy of mind). Real agency requires beliefs, desires, intentions, persistent goals, and ideally something like genuine autonomy. Excludes most current LLM systems.

6. The "embodied" camp (robotics, situated cognition). Without a physical body acting on a real environment, you have a chatbot rather than an agent. Excludes pure software systems entirely.

There is no canonical authority. There is no committee. The word is genuinely contested, and the contest is mostly about which properties matter for the work you are trying to do. A robotics researcher cares about embodiment because their problems involve real sensors and noise. An LLM engineer focuses on control-flow autonomy because that is the property that breaks their debugging tools. A philosopher cares about intentionality because they are asking whether the system is morally responsible. All three are correct *for their domain*, and they talk past each other *across domains*.

## A working definition for this course

We adopt the Anthropic distinction because it is the one that produces actionable engineering consequences. Specifically:

**Working Definition:**

> An agent is a system in which an LLM is invoked in a loop, given a set of tools and an objective, and the LLM itself decides, on each step, which tool to call, with what arguments, and when to terminate. 
> 
> A workflow is a system in which the LLM is invoked one or more times along control-flow paths that are fixed by the engineer at design time.
> 
> Both are agentic systems.

An agent under this definition has four operational properties. 
- It runs as a loop: the LLM is called more than once, with the results of earlier calls and actions visible in later calls.
- It uses tools: the LLM can take actions that affect some environment, whether that is the filesystem, network, database, code execution, or even other LLMs.
- Its control flow is autonomous: the LLM, not the engineer, decides what happens next at each step.
- Its termination is LLM-controlled: the loop ends when the LLM signals it is done (typically by not requesting a tool), not when a fixed pipeline finishes.

If your system has all four, you have an agent. If any are fixed by code, you have a workflow (or a more constrained agentic system). This definition is useful precisely because the engineering consequences differ on every axis:

| Property        | Workflow                 | Agent                         |
| --------------- | ------------------------ | ----------------------------- |
| Debugging       | Read the code            | Trace the LLM's decisions     |
| Cost modeling   | Approximately fixed      | Highly variable               |
| Latency         | Predictable              | Variable (often long)         |
| Failure modes   | Per-stage error handling | Whole-trajectory failure      |
| Evaluation      | Per-step correctness     | End-to-end behavior           |
| Safety boundary | Code enforces            | Prompts + sandboxing          |
| Output variance | Low                      | High                          |
| Best for        | Well-understood tasks    | Open-ended, exploratory tasks |

## The mental model to carry forward

An agent is the answer to the question: "What if we let the LLM decide what to do next?"

A workflow is the answer to the question: "What if we let the engineer decide what to do next, and the LLM only fills in specific slots?"

Both are valid. Both are 'agentic systems.' Neither is inherently better. The choice depends on:
- How dynamic is the task? (Predictable steps → workflow)
- How much output variance can you tolerate? (Low → workflow)
- How important is predictable cost? (High → workflow)
- Can you enumerate the necessary tool sequence? (Yes → workflow)
- Does the task require open-ended decision-making? (Yes → agent)
- Are the action paths discoverable only at runtime? (Yes → agent)

Anthropic's central engineering recommendation is to reach for a workflow, not an agent, unless the task genuinely requires open-ended decision-making. Agents look powerful because they look general; they appear to "just figure it out." In practice, that generality buys you variance, debugging pain, and cost overruns. Workflows are constrained but legible. Agents are flexible but opaque. A senior engineer chooses on purpose, not by default.
