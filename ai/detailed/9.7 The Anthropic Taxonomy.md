## Why a taxonomy at all?

In December 2024, Anthropic published *Building Effective Agents* (Schluntz & Zhang), a synthesis of patterns that emerged from working with dozens of teams putting LLMs into production. The conclusion was simple. The most successful implementations weren't using complex frameworks or specialized libraries; they used simple, composable patterns.

The taxonomy catalogs those patterns. It gives engineers a shared vocabulary for talking about how much autonomy an LLM-driven system has, and it imposes a design discipline: start with the simplest pattern that solves the problem, and reach for more complex ones only when measurement says you must. Anthropic puts the trade-off bluntly: agentic systems often trade latency and cost for better task performance, and you should consider when this tradeoff makes sense.

Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents, on the other hand, are systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks.

A workflow is a graph that you (the engineer) draw. An agent is a graph the LLM draws at runtime, edge by edge. Five of the seven patterns in the taxonomy are workflows. One is the foundational building block. The last is the agent itself. The progression from building block to workflow to agent is a progression of who controls the control flow.

```
WHO CONTROLS THE FLOW?

   you             Augmented LLM             building block
    ▲                    │
    │                    ▼
    │              Prompt Chaining           fixed linear pipeline
    │                    │
    │                    ▼
    │                 Routing                fixed branching
    │                    │                   (classifier picks one)
    │                    ▼
    │              Parallelization           fixed fan-out
    │                    │                   (sectioning or voting)
    │                    ▼
    │              Orchestrator-Workers      dynamic fan-out
    │                    │                   (LLM picks subtasks)
    │                    ▼
    │              Evaluator-Optimizer       fixed loop, LLM
    │                    │                   critiques itself
    ▼                    ▼
   LLM             Autonomous Agent          open loop, LLM
                                             decides each step
```

The patterns are not a strict hierarchy where each subsumes the last. They are a menu. The diagram orders them by how much trajectory-shaping authority you surrender to the model. Real systems often combine several at once.

## Pattern 0: The Augmented LLM (the building block)

Before there are "agents", there is the augmented LLM. This is a model that can do more than emit tokens conditioned on a prompt. The augmentations are:

1. **Retrieval.** The model can fetch external knowledge (documents, embeddings, database rows) into its context.
2. **Tools.** The model can call functions you expose (HTTP requests, code execution, file edits) and receive their results back as observations.
3. **Memory.** The model can persist and recall information across turns or sessions.

The current models can actively use these capabilities, generating their own search queries, selecting appropriate tools, and determining what information to retain.

```
                ┌──────────────┐
                │  Retrieval   │ ◄── corpora, vector stores, SQL
                └──────┬───────┘
                       │
                       ▼
   input ───────►┌──────────┐───────► output
                 │   LLM    │
                 └────┬─────┘
              ↑       │       ↑
              │       ▼       │
       ┌──────┴─┐  ┌─────┐  ┌─┴──────┐
       │ Memory │  │Tools│  │ Tools  │
       └────────┘  └─────┘  └────────┘
```

This is pattern zero because every other pattern in the taxonomy is built from augmented LLM calls. When the article uses a box labeled "LLM", it means an augmented LLM, not a raw next-token predictor. For the remainder, we'll assume each LLM call has access to these augmented capabilities.

A Model Context Protocol implementation is one way to wire the augmentations in cleanly; Anthropic recommends it directly: one approach is through the recently released Model Context Protocol, which allows developers to integrate with a growing ecosystem of third-party tools with a simple client implementation.

When to stop here: if a single augmented call with good prompting, retrieval, and a small toolset solves your problem, you are done. For many applications, however, optimizing single LLM calls with retrieval and in-context examples is usually enough.

## Pattern 1: Prompt Chaining

Prompt chaining decomposes a task into a sequence of steps, where each LLM call processes the output of the previous one. You can add programmatic checks on any intermediate steps to ensure that the process is still on track.

```
input ──► [LLM₁] ──► gate? ──► [LLM₂] ──► gate? ──► [LLM₃] ──► output
                       │                     │
                       ▼                     ▼
                   fail/retry            fail/retry
                     /abort               /abort
```

This is a Unix pipeline where each stage happens to be an LLM call. The "gates" are ordinary deterministic code (regex matches, schema validators, type guards, custom evals) that decide whether the intermediate output is good enough to continue.

**When to use.** This workflow is ideal for situations where the task can be easily and cleanly decomposed into fixed subtasks. The main goal is to trade off latency for higher accuracy, by making each LLM call an easier task.

Why does breaking a task into N sequential calls produce *higher* accuracy than one big call? Because each call has a narrower job. A model asked to "draft an outline AND write a 2,000-word doc that matches it" splits its attention across both subgoals. A model given a checked outline and asked only to expand it has all of its capacity on expansion. You are trading $N \times$ token cost and $N \times$ latency for sharper per-step performance.

**Canonical examples.** Generating Marketing copy, then translating it into a different language. Writing an outline of a document, checking that the outline meets certain criteria, then writing the document based on the outline.

**Failure modes to anticipate.**

Error compounding. Each stage is an independent source of error. Three 95%-accurate stages chained have $0.95^3 \approx 86\%$ end-to-end accuracy. The gates exist to halt the cascade before bad intermediates poison downstream calls.

Mid-chain drift. If stage $k$ produces output in a slightly off format, stage $k+1$ may silently degrade. Gates should validate schema, not just "did it return something".

## Pattern 2: Routing

Routing classifies an input and directs it to a specialized follow-up task. This workflow allows for separation of concerns, and building more specialized prompts. Without this workflow, optimizing for one kind of input can hurt performance on other inputs.

```
                            ┌─► [handler A] ─┐
                            │                │
input ──► classifier ───────┼─► [handler B] ─┼──► output
                            │                │
                            └─► [handler C] ─┘
```

Think of routing as a `switch` statement where the discriminator is computed by an LLM (or by a cheap classical classifier, such as a `tfidf + logistic regression`, a regex set, or a small embedding-based nearest-neighbor lookup). Any classifier that produces a label reliably will do. Each branch is then a different prompt, possibly a different model, possibly a different toolset.

Why it works: a single prompt that has to handle "general questions", "refund requests", and "technical support" must contain instructions for all three, plus disambiguation logic, plus all the tool definitions. That is a lot of context for the model to juggle, and it tends to interfere with itself. Routing lets each branch's prompt stay small, focused, and tunable independently.

**When to use.** Routing works well for complex tasks where there are distinct categories that are better handled separately, and where classification can be handled accurately, either by an LLM or a more traditional classification model/algorithm.

Two non-negotiable preconditions:

1. The categories are genuinely distinct. Overlap is a smell. If you find categories overlapping, re-cut the taxonomy or move to parallelization.
2. The classifier is reliable. A bad classifier turns one well-tuned system into N poorly-routed systems.

**Canonical examples.** Directing different types of customer service queries (general questions, refund requests, technical support) into different downstream processes, prompts, and tools. Routing easy/common questions to smaller, cost-efficient models like Claude Haiku 4.5 and hard/unusual questions to more capable models like Claude Sonnet 4.5 to optimize for best performance.

The second example deserves its own remark. Routing is also a cost-optimization primitive. If 80% of your traffic is easy, a router that sends those to Haiku and the other 20% to Sonnet can reduce spend by an order of magnitude with no quality regression. The "with no regression" part is conditional on measurement.

**Failure modes to anticipate.**

Ambiguous inputs. A query that is both a refund request and a technical complaint gets force-routed to one branch. Track the classifier's confidence and fall back to a generalist branch (or escalate to a human) below a threshold.

Concept drift. As your product changes, new query types appear that do not fit the taxonomy. Log misroutes and retrain.

## Pattern 3: Parallelization

LLMs can sometimes work simultaneously on a task and have their outputs aggregated programmatically. The pattern has two flavors:

1. Sectioning. Breaking a task into independent subtasks run in parallel.
2. Voting. Running the same task multiple times to get diverse outputs.

```
SECTIONING (each branch sees a different sub-aspect)

            ┌─► [LLM: aspect A] ─┐
input ──────┼─► [LLM: aspect B] ─┼──► aggregator ──► output
            └─► [LLM: aspect C] ─┘

VOTING (each branch sees the same task)

            ┌─► [LLM: attempt 1] ─┐
input ──────┼─► [LLM: attempt 2] ─┼──► vote/quorum ──► output
            └─► [LLM: attempt 3] ─┘
```

Sectioning is map-reduce, where the map step is "give each LLM a slice of the problem" and the reduce step is deterministic aggregation. Use it when the problem decomposes cleanly along orthogonal dimensions. Security review, performance review, and style review of the same code are a good example. They are different concerns, and each LLM gets its own focused prompt.

Voting is a Monte Carlo trick. Because LLM outputs are stochastic (sampled at $T > 0$), running the same query $n$ times produces a distribution. Aggregating that distribution (majority vote, threshold, consensus) reduces variance. For binary classification tasks this is a direct instance of an ensemble method.

Formally, if individual call accuracy is $p$ and errors are independent, the probability that a majority-vote ensemble of $n$ calls is correct is:

$$\sum_{k=\lceil n/2 \rceil}^{n} \binom{n}{k} p^k (1-p)^{n-k}$$

which exceeds $p$ for $p > 0.5$. In practice errors are not independent (models share blind spots), so the gain is real but less than this bound suggests.

**When to use.** Parallelization is effective when the divided subtasks can be parallelized for speed, or when multiple perspectives or attempts are needed for higher confidence results. For complex tasks with multiple considerations, LLMs generally perform better when each consideration is handled by a separate LLM call, allowing focused attention on each specific aspect.

**Canonical examples.**

Sectioning: Implementing guardrails where one model instance processes user queries while another screens them for inappropriate content or requests. This tends to perform better than having the same LLM call handle both guardrails and the core response. A second example: Automating evals for evaluating LLM performance, where each LLM call evaluates a different aspect of the model's performance on a given prompt.

Voting: Reviewing a piece of code for vulnerabilities, where several different prompts review and flag the code if they find a problem. Another: Evaluating whether a given piece of content is inappropriate, with multiple prompts evaluating different aspects or requiring different vote thresholds to balance false positives and negatives.

**Trade-offs.** You pay $n \times$ token cost for $n$ parallel calls. Latency stays roughly flat (the slowest branch wins) if your provider supports concurrency. Use voting sparingly. Its gains diminish quickly, and its costs scale linearly. Two or three voters often capture most of the benefit.

## Pattern 4: Orchestrator-Workers

In the orchestrator-workers workflow, a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results.

```
                ┌──────────────┐
input ─────────►│ Orchestrator │
                │     LLM      │
                └──────┬───────┘
            (dynamically plans tasks)
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
   [Worker LLM]   [Worker LLM]   [Worker LLM]
        │              │              │
        └──────────────┼──────────────┘
                       ▼
                  ┌─────────┐
                  │Synthesis│ ──► output
                  └─────────┘
```

This is map-reduce again, but the orchestrator decides at runtime how many mappers run and what each one does. The important difference from sectioning-style parallelization is laid out explicitly in the source. Whereas it's topographically similar, the key difference from parallelization is its flexibility. Subtasks are not pre-defined. They are determined by the orchestrator based on the specific input.

In sectioning, you hard-code "split this into aspect A, B, C". In orchestrator-workers, the LLM looks at the input and decides "this task needs me to edit files X, Y, Z", and your code could not have known how many files in advance.

**When to use.** This workflow is well-suited for complex tasks where you can't predict the subtasks needed (in coding, for example, the number of files that need to be changed and the nature of the change in each file likely depend on the task).

This is the pattern most coding assistants use to handle multi-file edits. The orchestrator reads the task description, decides which files to touch, dispatches a worker (often with a focused prompt and only the relevant file's context) per file, and then a synthesis step composes the patch.

**Canonical examples.** Coding products that make complex changes to multiple files each time. Search tasks that involve gathering and analyzing information from multiple sources for possible relevant information.

**Failure modes.**

Bad plans. If the orchestrator plans poorly (misses a file, double-counts an aspect), the workers downstream cannot recover. Quality is bottlenecked by the orchestrator.

Context bloat in synthesis. The synthesis step sees every worker's output. For ten workers each producing a 1k-token edit, synthesis must reason over 10k tokens. Consider hierarchical synthesis (workers in groups, then group synthesizers, then a final synthesizer) for fan-outs beyond a handful.

## Pattern 5: Evaluator-Optimizer

In the evaluator-optimizer workflow, one LLM call generates a response while another provides evaluation and feedback in a loop.

```
       ┌──────── feedback ──────────────────────────────────────┐
       │                                                        │
       ▼                                                        │
input ──► [Generator] ──► draft ──► [Evaluator]                 │
                                         │                      │
                                         ▼                      │
                                    acceptable?                 │
                                         │                      │
                               ┌─────────┴─────────┐            │
                               ▼                   ▼            │
                              yes ──► output       no ──────────┘
```

This is a two-actor system: a writer and a critic. The critic produces structured feedback that the writer consumes on the next iteration. The loop is bounded by either (a) the critic saying "acceptable", (b) a maximum iteration count, or (c) a convergence check (feedback stops changing materially).

**When to use.** This workflow is particularly effective when we have clear evaluation criteria, and when iterative refinement provides measurable value. The two signs of good fit are:

1. Human feedback would help. If a domain expert critiquing the output would improve it, then an LLM-as-critic stands a chance.
2. The LLM can supply that feedback. If the critique requires expertise the model lacks (specialized law, novel science), the loop will hallucinate critique and degrade output.

**Canonical examples.** Literary translation where there are nuances that the translator LLM might not capture initially, but where an evaluator LLM can provide useful critiques. Complex search tasks that require multiple rounds of searching and analysis to gather comprehensive information, where the evaluator decides whether further searches are warranted.

**Trade-offs.**

Costs scale with the number of rounds (typically 2 to 5 in practice). Evaluator collusion is a real risk. If generator and evaluator are the same model with the same blind spots, you can loop forever convinced the output is good. Use a different model, a different prompt, or both for the evaluator. The convergence criterion matters enormously. "Acceptable" should be operationalized as concrete checks the evaluator can actually verify.

## Pattern 6: The Autonomous Agent

Where the previous five patterns are workflows, this is the agent. Anthropic's framing:

Agents begin their work with either a command from, or interactive discussion with, the human user. Once the task is clear, agents plan and operate independently, potentially returning to the human for further information or judgement. During execution, it's crucial for the agents to gain "ground truth" from the environment at each step (such as tool call results or code execution) to assess its progress. Agents can then pause for human feedback at checkpoints or when encountering blockers.

The deceptively simple structural claim: Agents can handle sophisticated tasks, but their implementation is often straightforward. They are typically just LLMs using tools based on environmental feedback in a loop.

```
                   human request
                        │
                        ▼
                  ┌──────────┐
                  │  Agent   │◄─────────────────┐
                  │   LLM    │                  │
                  └────┬─────┘                  │
                       │                        │
                (reason: choose                 │
                tool, or stop)                  │
                       │                        │
                       ▼                        │
                  use tool? ──── no ──► return result
                       │ yes                    │
                       ▼                        │
                ┌────────────┐                  │
                │ Environment│ ──► observation ─┘
                │ (executes  │
                │   tool)    │
                └────────────┘
```

The agentic loop in pseudocode is just:

```
while not done and iterations < limit:
    response = LLM(history, tools)
    if response.stop_reason == "end_turn":
        return response.text
    observations = [execute(call) for call in response.tool_calls]
    history.append(response)
    history.append(observations)
```

That is the entire skeleton. Everything else is engineering around it: tool design, history compaction, checkpoint UI, sandboxing.

**When to use.** Agents can be used for open-ended problems where it's difficult or impossible to predict the required number of steps, and where you can't hardcode a fixed path. The LLM will potentially operate for many turns, and you must have some level of trust in its decision-making. Agents' autonomy makes them ideal for scaling tasks in trusted environments.

Two trust gates here are easy to skip past. Do not skip them. "Trust in its decision-making" is earned through extensive evals. "Trusted environments" means sandboxed, with destructive operations either gated by humans or made reversible.

**Cost profile.** The autonomous nature of agents means higher costs, and the potential for compounding errors. We recommend extensive testing in sandboxed environments, along with the appropriate guardrails.

**Canonical examples.** A coding Agent to resolve SWE-bench tasks, which involve edits to many files based on a task description; Our "computer use" reference implementation, where Claude uses a computer to accomplish tasks.

A few details that matter in production:

Halting. A maximum iteration count is mandatory. Never trust the model's `end_turn` alone to guarantee termination.

History compaction. Long agent runs hit context limits. Strategies include summarization passes, sliding windows, and structured scratchpads.

Human-in-the-loop checkpoints. Pausing for confirmation before destructive operations is one of the most common safety patterns in deployed agents.

Tool design dominates. From the article: While building our agent for SWE-bench, we actually spent more time optimizing our tools than the overall prompt.

## Where the academic literature connects

The cited papers predate (or were contemporaneous with) the Anthropic taxonomy and provide the research underpinnings for the autonomous-agent pattern specifically. Treat them as the primary literature on agent internals. The Anthropic taxonomy is the practitioner synthesis.

**ReAct (Yao et al., ICLR 2023): "ReAct: Synergizing Reasoning and Acting in Language Models."** The core proposal: interleave thought tokens (the model's reasoning chain, written in natural language) with action tokens (tool invocations) and observation tokens (returns from the environment). The loop is:

$$\text{thought}_t \to \text{action}_t \to \text{observation}_t \to \text{thought}_{t+1} \to \ldots$$

ReAct is essentially the academic specification of the autonomous-agent pattern's inner loop. When the Anthropic article says "LLMs using tools based on environmental feedback in a loop", it is describing the ReAct loop. The insight ReAct contributed: making the reasoning visible as tokens (not hidden in the model's internal state) lets the model self-correct and lets engineers debug. That connects directly to the "transparency" principle Anthropic lists.

**Reflexion (Shinn et al., NeurIPS 2023)** adds an explicit self-reflection step after failed attempts. The agent writes a natural-language critique of its own trajectory, stores it in long-term memory, and consults it on subsequent attempts. This is structurally an evaluator-optimizer wrapped around an agent. The inner agent generates a trajectory, the reflection step evaluates it, and the feedback re-enters as memory for the next try. If you read the Anthropic taxonomy as building blocks, Reflexion is evaluator-optimizer composed with autonomous agent.

**Tree of Thoughts (Yao et al., NeurIPS 2023)** generalizes Chain-of-Thought from a linear reasoning trace to a tree, with explicit branch exploration, evaluation of partial states, and backtracking. The shape is closer to classical search (BFS/DFS/beam) over reasoning states. In the Anthropic taxonomy this maps onto a combination of orchestrator-workers (the orchestrator expands the frontier) and parallelization (multiple branches explored concurrently), with an evaluator pruning the tree.

## Choosing the right pattern

A decision procedure derived from the source's guidance. Walk these in order. The first match wins.

```
START
  │
  ▼
Does a single augmented LLM call (with retrieval, tools) solve it?
  ├─ yes ──► AUGMENTED LLM. Stop.
  └─ no
       │
       ▼
Can the task be decomposed into a fixed sequence of well-defined steps?
  ├─ yes ──► PROMPT CHAINING.
  └─ no
       │
       ▼
Is the input one of N distinct categories, each better handled separately?
  ├─ yes ──► ROUTING.
  └─ no
       │
       ▼
Can subtasks be enumerated in advance and run independently?
  ├─ yes ──► PARALLELIZATION (sectioning).
  └─ no (or you need consensus on a single answer)
       │
       ▼
Do you need multiple independent attempts at the same task for confidence?
  ├─ yes ──► PARALLELIZATION (voting).
  └─ no
       │
       ▼
Do subtasks depend on the input in ways you cannot enumerate in advance,
but a planning step can?
  ├─ yes ──► ORCHESTRATOR-WORKERS.
  └─ no
       │
       ▼
Is there clear evaluation criteria where iterative critique improves output?
  ├─ yes ──► EVALUATOR-OPTIMIZER.
  └─ no
       │
       ▼
Is the trajectory genuinely open-ended, requiring the model to decide each step,
AND is the environment sandboxed / can you afford the cost & error budget?
  ├─ yes ──► AUTONOMOUS AGENT.
  └─ no ───► Reconsider. The problem may not be a good fit for LLMs, or
             needs to be re-specified into a workflow.
```

## Composition: the patterns are building blocks

The most important thing about the taxonomy is that it is not prescriptive. They're common patterns that developers can shape and combine to fit different use cases. The key to success, as with any LLM features, is measuring performance and iterating on implementations.

Real systems compose:

A customer-support system might route by intent, chain retrieval-then-response within the "general question" branch, run an autonomous agent for the "complex troubleshooting" branch, and apply parallel guardrails on every output.

A coding system might be orchestrator-workers at the file level, with each worker an autonomous agent that edits one file using tools, with an evaluator-optimizer loop on the synthesized patch (run tests, feed failures back to the generator).

A research system might be an agent at the top level, but use parallelization for source review and prompt chaining for the summary-then-citation step.

Treat the taxonomy as a vocabulary for thinking about your architecture. It is not a menu where you pick one entry.

## The three core principles

The three principles that govern every choice in the taxonomy.
1. Maintain simplicity in your agent's design.
2. Prioritize transparency by explicitly showing the agent's planning steps.
3. Carefully craft your agent-computer interface (ACI) through thorough tool documentation and testing.

These are not platitudes. Each maps to a concrete engineering practice.

Simplicity. If prompt chaining solves your problem, do not reach for an autonomous agent. Complexity has a cost paid in dollars, latency, and debugging time.

Transparency. Make the model's reasoning, plans, and tool calls visible in your logs and ideally in your UI. ReAct-style externalized reasoning is a debugging affordance, not just a research contribution.

ACI quality. One rule of thumb is to think about how much effort goes into human-computer interfaces (HCI), and plan to invest just as much effort in creating good agent-computer interfaces (ACI). Tools are how the agent touches the world. Bad tool design is the most common failure mode in production agents.
