## The problem ReAct was designed to solve

Before ReAct, LLMs were used for multi-step problem solving in two largely disjoint ways.

```
┌────────────────────────────────────────────────────────────┐
│                  Mode A: Reasoning only                    │
│                                                            │
│  Chain-of-Thought (Wei et al., 2022).                      │
│  The model emits a sequence of natural-language reasoning  │
│  steps before its final answer.                            │
│                                                            │
│  Example:                                                  │
│    Q: If Alice has 3 apples and Bob gives her twice as     │
│       many as she has, how many does she have?             │
│    Thought: She has 3. Bob gives 2 * 3 = 6.                │
│    Thought: 3 + 6 = 9.                                     │
│    Answer: 9                                               │
│                                                            │
│  Failure mode: Reasoning is internal. The model cannot     │
│  look anything up, cannot check its work, and any factual  │
│  premise it invents stays unverified. Hallucinations       │
│  compound across steps.                                    │
└────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────┐
│                  Mode B: Acting only                       │
│                                                            │
│  WebGPT (Nakano et al., 2021), SayCan (Ahn et al.,         │
│  2022). The model emits actions (search queries,           │
│  robot commands) and receives observations back.           │
│                                                            │
│  Failure mode: Actions are blind. The model has no scratch │
│  space to plan, to decide why an observation matters, or   │
│  to compose a multi-step plan conditioned on what it just  │
│  saw.                                                      │
└────────────────────────────────────────────────────────────┘
```

Yao et al. observed something that looks obvious in hindsight. Humans do not separate these two modes. When you research a question, you alternate. You think about what you need, look it up, read the result, think about whether it answered your question, then decide your next move.

> Reasoning lets you plan actions. Actions feed information back into your reasoning.

ReAct is the architectural realization of that observation.

## The core pattern

A ReAct agent runs a loop. Each iteration produces three text blocks in sequence:

```
       ┌─────────┐     ┌─────────┐     ┌─────────────┐
   ┌──▶│ Thought │ ──▶ │ Action  │ ──▶ │ Observation │ ──┐
   │   └─────────┘     └─────────┘     └─────────────┘   │
   │                                                     │
   └──────────────────────── loop ───────────────────────┘
```

Formally, at step $t$ the model produces a tuple $(\tau_t, a_t)$ where $\tau_t$ is a free-form thought and $a_t$ is an action drawn from a finite set $\mathcal{A}$. The environment returns an observation $o_t$. The next prompt is the entire history:

$$\text{prompt}_t \;=\; \bigl[\,q,\; (\tau_1, a_1, o_1),\; (\tau_2, a_2, o_2),\;\dots,\;(\tau_{t-1}, a_{t-1}, o_{t-1})\,\bigr]$$

where $q$ is the original query. The loop terminates when $a_t$ is a special `Finish(answer)` action, or when a step budget is exceeded.

The textual protocol Yao et al. used for HotpotQA:

- Question: `<user question>`
- Thought 1: `<free-form reasoning>`
- Action 1:  `Search(<term>)` | `Lookup(<keyword>)` | `Finish(<answer>)`
- Observation 1: `<returned text>`
- Thought 2: ...
- Action 2:  ...
- Observation 2: ...
- ...

Three things to notice. They are the whole pattern.

1. Thoughts are not actions. They have no side effects. They exist only to condition the next action. This is the channel where the model plans, hypothesizes, and self-corrects.

2. Actions are typed. The model picks from a finite menu (in the original paper: `Search`, `Lookup`, `Finish`). The action space defines the agent's capabilities. Anything outside the menu is invalid.

3. Observations are not generated by the model. They are appended by the orchestrator after the action runs against the real environment. This is the critical distinction from pure chain-of-thought: the trace contains real external information.

## Why it works, mechanistically

The reason ReAct outperforms both CoT-only and act-only baselines is best understood through the two failure modes it suppresses at the same time.

### Reasoning errors get caught by observation

In pure CoT, the model might emit:

- Thought: The Eiffel Tower was completed in 1887.
- Thought: That's 35 years before the Empire State Building (1922).
- Thought: So the Empire State Building was completed in 1922.
- Answer: 1922

Both premises are wrong (Eiffel Tower opened 1889, Empire State opened 1931), and the conclusion is wrong, but the chain is locally coherent. Each step follows from the previous. CoT has no mechanism to detect the factual error.

In ReAct:

- Thought: I should check the year the Empire State Building opened.
- Action: `Search(Empire State Building)`
- Observation: The Empire State Building is a 102-story Art Deco skyscraper... completed in 1931.
- Thought: So it was 1931.
- Action: `Finish(1931)`

The observation is ground truth, so reasoning errors that affect the action selection get caught the moment the model has to commit.

### Action errors get caught by reasoning

In pure-action systems, the model might emit:

```
Search(Eiffel Tower height)   →   "330 metres"
Search(Eiffel Tower height)   →   "330 metres"
Search(Eiffel Tower height)   →   "330 metres"
```

It has no place to write "I already have this, I need the next thing." A thought step gives the model that place:

- Thought: I know the Eiffel Tower is 330m. Now I need the height of the Burj Khalifa to compare.
- Action:  `Search(Burj Khalifa height)`

In information-theoretic terms, the thought channel lets the model condense the observation history into a working hypothesis for the next action, without re-reading the entire observation log on every step.

### The trace is external memory

This is the subtlest point and the most important. The model has no internal memory across forward passes. Every call is stateless. The Thought-Action-Observation log *is* the agent's state, and that log gets re-injected verbatim on every step.

Three consequences worth burning in now.

- The trace must be re-tokenized and re-attended every step. Context costs grow linearly.
- Anything not in the trace is forgotten. Memory architectures exist precisely to manage what stays.
- Self-correction is possible because the model can re-read its own earlier thoughts and notice contradictions with new observations.

On HotpotQA, Yao et al. report that ReAct cuts the hallucination rate of CoT-only agents substantially while solving more questions correctly.

## A worked example

Question: *"What is the elevation range of the area in the eastern sector of the Colorado orogeny?"*

- Thought 1: I need to search the Colorado orogeny, find the area of its eastern sector, then find the elevation.
- Action 1: `Search[Colorado orogeny]`
- Observation 1: The Colorado orogeny was an episode of mountain building (an orogeny) in Colorado and surrounding areas.
- Thought 2: The result doesn't mention the eastern sector. I need to look up "eastern sector".
- Action 2:  `Lookup[eastern sector]`
- Observation 2: The eastern sector extends into the High Plains and is called the Central Plains orogeny.
- Thought 3: Now I need the elevation of the High Plains.
- Action 3:  `Search[High Plains]`
- Observation 3: The High Plains rise in elevation from around 1,800 to 7,000 ft.
- Thought 4: The High Plains rise from 1,800 to 7,000 ft. That's the answer.
- Action 4:  `Finish[1,800 to 7,000 ft]`

Trace through this carefully.

Thought 1 decomposes the question into a plan. The model commits to a multi-step strategy before any action runs. It does planning in the prompt. Thought 2 reacts to Observation 1: the first search did not answer the sub-question, so the model adapts. Thought 3 chains, with the answer to sub-question 1 ("eastern sector = High Plains") becoming the input to sub-question 2 ("elevation of High Plains"). Thought 4 confirms that the question is now answered, which gates the `Finish` action.

This is not a script. The model decides at each step, conditioned on everything it has seen, whether the next action is a search, a lookup, or termination.

## Implementation in TypeScript

Below is a complete, runnable ReAct loop that mirrors the structure of Yao et al.'s original prompt format. Modern tool-use APIs abstract away the text parsing, but implementing it from scratch is the only way to see what those abstractions are doing.

```typescript
type ToolName = "search" | "lookup" | "finish";

type Action = {
  readonly tool: ToolName;
  readonly argument: string;
};

type Step = {
  readonly thought: string;
  readonly action: Action;
  readonly observation: string;
};

type ReactResult =
  | { readonly status: "answered"; readonly answer: string; readonly trace: readonly Step[] }
  | { readonly status: "budget_exhausted"; readonly trace: readonly Step[] }
  | { readonly status: "parse_error"; readonly trace: readonly Step[] };

/**
 * Tool dispatcher. In a real system this would call external APIs,
 * a vector DB, a code executor, etc. Tools are a flat record of
 * (name -> async function), so adding a new tool is a one-line change.
 *
 * `finish` is intentionally not in the table. It is handled by the
 * orchestrator, not by an external tool.
 */
type ToolTable = Readonly<Record<Exclude<ToolName, "finish">, (arg: string) => Promise<string>>>;

type LLM = (prompt: string) => Promise<string>;

const MAX_STEPS = 10 as const;

const SYSTEM_PROMPT = `
You solve questions by interleaving Thought, Action, Observation steps.
Available actions:
  search[term]   : search a knowledge base for the term
  lookup[term]   : find the next occurrence of the term in the current
                   search result
  finish[answer] : emit the final answer and stop

Output exactly one Thought and one Action per step. Do NOT generate
Observations. Those are provided by the environment.
`;

/**
 * Parses one ReAct step from the model's raw text output.
 * Returns null if the text does not contain a valid step. The
 * caller treats this as a model error and aborts. (A more
 * forgiving system would send a corrective prompt and retry.)
 *
 * NOTE: production systems should use structured output (JSON
 * schema, tool-use API) instead of regex parsing. This is shown
 * only to expose the underlying protocol.
 */
const parseStep = (raw: string): { thought: string; action: Action } | null => {
  const thoughtMatch = raw.match(/Thought\s*\d*:\s*([\s\S]*?)\nAction\s*\d*:/);
  const actionMatch = raw.match(/Action\s*\d*:\s*(\w+)\[([\s\S]*?)\]/);

  if (thoughtMatch === null || actionMatch === null) {
    return null;
  }

  const toolRaw = actionMatch[1].toLowerCase();

  if (toolRaw !== "search" && toolRaw !== "lookup" && toolRaw !== "finish") {
    return null;
  }

  return {
    thought: thoughtMatch[1].trim(),
    action: { tool: toolRaw as ToolName, argument: actionMatch[2].trim() },
  };
};

/**
 * Serializes the running trace back into the format the model was
 * prompted with. The full trace is re-injected on every forward
 * pass because the model is stateless.
 */
const serializeTrace = (trace: readonly Step[]): string => {
  const parts = new Array<string>(trace.length);

  for (let i = 0; i < trace.length; i++) {
    const s = trace[i];

    parts[i] =
      `Thought ${i + 1}: ${s.thought}\n` +
      `Action ${i + 1}: ${s.action.tool}[${s.action.argument}]\n` +
      `Observation ${i + 1}: ${s.observation}`;
    }

    return parts.join("\n");
};

const runReAct = async (
  question: string,
  llm: LLM,
  tools: ToolTable,
): Promise<ReactResult> => {
  const trace: Step[] = [];

  for (let step = 0; step < MAX_STEPS; step++) {
    const prompt =
      SYSTEM_PROMPT +
      `\nQuestion: ${question}\n` +
      (trace.length > 0 ? serializeTrace(trace) + "\n" : "") +
      `Thought ${step + 1}:`;

    const raw = await llm(prompt);
    const parsed = parseStep(`Thought ${step + 1}: ${raw}`);

    if (parsed === null) {
      return { status: "parse_error", trace };
    }

    const { thought, action } = parsed;

    if (action.tool === "finish") {
      trace.push({ thought, action, observation: "" });
      return { status: "answered", answer: action.argument, trace };
    }

    const observation = await tools[action.tool](action.argument);
    trace.push({ thought, action, observation });
  }

  return { status: "budget_exhausted", trace };
};
```

A few implementation choices worth understanding.

The full trace gets re-sent every iteration. The model is stateless. Anything from earlier steps that you want the model to remember has to live in the prompt. This is the main efficiency concern of the pattern: every additional step makes every subsequent step's prompt longer. A 10-step ReAct trace's final prompt contains the cumulative tokens of all nine prior steps.

`MAX_STEPS` is a hard safety bound. Without it, a buggy model can loop forever. Yao et al. used 7 steps for HotpotQA. Modern systems typically allow 10 to 50 depending on task complexity, and computer-use agents push into the hundreds.

`finish` is just another action. This is the canonical way to let the model decide its own stopping point. Termination is a choice the model makes, not a heuristic the orchestrator imposes. The orchestrator only imposes the upper bound.

Parsing is fragile. The original ReAct paper used regex parsing like the above. Modern LLM APIs (Anthropic tool use, OpenAI function calling, Gemini function calling) expose actions as structured JSON, which makes the parse step trivial. The underlying protocol is unchanged.

Tools are pure functions of strings. This is deliberately minimal. Real tool tables return rich, sometimes structured, observations, but the function shape stays the same.

## Failure modes

ReAct is not a panacea. The four most common failure modes:

### Reasoning loops

The model keeps emitting variants of the same thought without making progress:

- Thought 5: I should search for the population of France.
- Action 5:  `Search(population of France)`
- Observation 5: France's population is 67 million.
- Thought 6: I should search for the population of France.
- Action 6:  `Search(population of France)`
- ...

Mitigation: prior observations are already in the prompt (the protocol guarantees this), so it usually suffices to add a "stuck detector" that fires when the same action repeats within a window.

### Premature finishing

The model emits `Finish` with a wrong or incomplete answer because it failed to notice that a sub-question remained unanswered. Mitigation: prompt with explicit self-check instructions before `Finish`, or use Reflexion (next section) to learn from this failure across attempts.

### Tool misuse

The model invents arguments the tool cannot handle, or picks the wrong tool. Mitigation: rigorous action-space documentation in the prompt, structured-output schemas that fail fast on invalid arguments, and post-execution validation that surfaces clear error messages back as observations, so the model can correct course.

### Context bloat

Long traces consume token budget. A 30-step trace can blow past the useful working window of even large-context models. Mitigation: summarize older steps into a condensed observation, drop irrelevant intermediate steps, or use external memory.

## Extension I: Reflexion (Shinn et al., NeurIPS 2023)

ReAct handles within-episode learning. The model can correct itself during a single trace. It cannot, however, learn from a failed episode that has terminated. If the agent gets a question wrong, the next time it sees the same question (or a similar one), it has no memory of why it failed.

Reflexion adds an extra component. After a trial completes, an *evaluator* assigns a signal (succeeded or failed, or a scalar reward). If the trial failed, a *self-reflection* step runs. The model reads the trace and generates a short verbal lesson. For example: "I confused the Colorado orogeny with the Colorado Plateau. Next time, I should verify which geographic region the question refers to before searching."

That reflection gets stored in an *episodic memory* and prepended to the next trial's prompt. The model now starts the new attempt with verbal advice from its own prior failure.

```
┌─────────────────────────────────────────────────────────────┐
│                       Reflexion architecture                │
│                                                             │
│   ┌─────────┐    trajectory    ┌───────────┐                │
│   │  Actor  │ ───────────────▶ │ Evaluator │                │
│   │ (ReAct) │                  └────┬──────┘                │
│   └────▲────┘                       │                       │
│        │                            │ reward / pass-fail    │
│        │ verbal advice              ▼                       │
│        │ prepended to          ┌───────────┐                │
│        │ next attempt          │ Reflector │                │
│        │                       └────┬──────┘                │
│        │                            │                       │
│        │                            ▼ verbal feedback       │
│        │                      ┌────────────┐                │
│        └───────────────────── │  Episodic  │                │
│                               │   Memory   │                │
│                               └────────────┘                │
└─────────────────────────────────────────────────────────────┘
```

Shinn et al. call this "verbal reinforcement learning" because the policy update gets delivered in natural language. No gradient steps, no weight changes. The model's prompt is what gets updated, not its parameters.

Empirically, Reflexion improves over plain ReAct on HumanEval (programming), AlfWorld (text-based household tasks), and HotpotQA. The cost is one extra reflection forward pass per failed trial, plus memory growth that is linear in the number of trials.

The conceptual point to internalize:

> Reflexion is to ReAct what cross-episode learning is to within-episode learning. ReAct's loop runs inside a single attempt. Reflexion's loop runs across attempts.

## Extension II: Tree of Thoughts (Yao et al., NeurIPS 2023)

ReAct is linear. At each step, the model commits to one thought, then one action, then sees one observation. If a thought leads down a bad path, the agent has to recognize the dead end and back out, which it may do poorly.

Tree of Thoughts (ToT) generalizes this. Instead of a single chain, the model expands a tree of partial reasoning states. At each node:

1. The model generates $k$ candidate thoughts (children).
2. The model rates each candidate (for example, "sure" / "maybe" / "impossible", or a numeric score).
3. A classical search algorithm (BFS or DFS) selects which nodes to expand next, optionally pruning low-rated branches.
4. Search terminates when a leaf is rated as a valid solution, or the budget is exhausted.

```
                              ROOT
                          (question)
                            /  |  \
                          T1   T2   T3        candidate thoughts
                         /  \         \
                        T11 T12       T31     expanded
                       sure maybe    sure
                        |              |
                        ▼              ▼
                     solution?     solution?
```

Yao et al. demonstrate ToT on Game of 24 (arithmetic puzzles), Creative Writing, and Mini Crosswords. On Game of 24, GPT-4 with CoT solves about 4% of instances. With ToT and DFS, GPT-4 solves 74%. The gain comes entirely from the search structure (same base model).

The relationship to ReAct:

- ReAct is a linear chain of (Thought, Action, Observation).
- ToT is a tree of Thoughts, with a self-evaluation function and a search algorithm.

These extensions are orthogonal. You can in principle combine them, building a tree of ReAct nodes. That combination is uncommon because the branching factor of search interacts badly with the cost of executing real-world actions. Every branch you expand means real HTTP requests, real shell commands, and so on.

The two patterns tend to fit different task shapes. ToT is preferred when the task is a closed-world reasoning problem with a clear self-evaluation function: math puzzles, planning, constrained generation. ReAct is preferred when the task requires open-world information gathering (research questions, code editing, web navigation), where you can't enumerate the action space ahead of time.

## Comparing the family at a glance

| Pattern          | Reasoning in trace | External actions | Cross-attempt memory | Structure                        |
| ---------------- | ------------------ | ---------------- | -------------------- | -------------------------------- |
| Chain-of-Thought | Yes                | No               | No                   | Linear                           |
| Act-only         | No                 | Yes              | No                   | Linear                           |
| ReAct            | Yes                | Yes              | No                   | Linear                           |
| Reflexion        | Yes                | Yes              | Yes (verbal)         | Linear, with episodic outer loop |
| Tree of Thoughts | Yes                | Optional         | No                   | Tree (BFS/DFS)                   |

Modern agent design is some recombination of those four dimensions.

## Anthropic's framing: when to use this at all

The academic literature treats ReAct as a target, something to build. Anthropic's 2024 guide "Building Effective Agents" treats it as a tool with a cost, and gives a more disciplined framing of when to reach for it.

The guide distinguishes two things.

Workflows are systems where LLMs and tools get composed through predefined code paths. Examples include prompt chaining, routing, parallelization, and evaluator-optimizer. The control flow is fixed. The model fills in content.

Agents are systems where the LLM dynamically directs its own process and tool usage. Control flow emerges from the model's choices. ReAct is the canonical agent pattern.

The main recommendation: use the simplest pattern that works. Workflows are cheaper, faster, more predictable, and easier to debug than agents. Reach for an agent only when:

- The task requires open-ended decisions about which sub-step comes next.
- The number of steps cannot be known in advance.
- The model's judgment at each step is genuinely needed to make progress.

This is a useful counterweight to the academic framing. Every ReAct step is a forward pass. A 10-step trace costs roughly 10x the latency and tokens of a single completion. If the task decomposes into a fixed chain ("extract entities, then look up each entity, then summarize"), prefer a workflow.

A useful decision heuristic distilled from the guide:

```
┌──────────────────────────────────────────────────────────────────┐
│                                                                  │
│  Is the control flow knowable in advance?                        │
│                                                                  │
│     ├── YES ─▶  Use a workflow. Cheaper, faster, debuggable.     │
│     │                                                            │
│     └── NO  ─▶  Does the task require many tool calls            │
│                 whose results inform later choices?              │
│                                                                  │
│                    ├── YES ─▶  ReAct-style agent.                │
│                    │                                             │
│                    └── NO  ─▶  Single completion with tools.     │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

## The modern picture

The ReAct paper is from 2022. Since then:

Tool-use APIs (Anthropic tool use, OpenAI function calling, Gemini function calling) bake the Thought-Action-Observation protocol into structured JSON. The model emits a `tool_use` block with arguments. The orchestrator emits a `tool_result`. The protocol is identical to ReAct. The parsing is no longer the developer's problem.

Native model training matters too. Frontier models are now post-trained on agentic traces, so ReAct-style behaviour is the default rather than something you few-shot-prompt into them. The original paper devoted significant space to crafting in-context examples. Modern usage rarely needs them.

Multi-tool, multi-step is the norm. Modern coding assistants, research agents, and computer-use agents are all ReAct loops at heart. They just have larger action spaces (file edits, shell commands, browser actions) and larger step budgets.

The conceptual pattern from Yao et al. (2022) has not changed. What has changed is that it is now infrastructure, not a research result.

## The mental model to take with you

```
┌────────────────────────────────────────────────────────────────┐
│            (stateless model + stateful trace)                  │
│                                                                │
│    query ──┐                                                   │
│            ▼                                                   │
│        ┌──────┐    Thought t      ┌──────┐                     │
│        │      │ ──────────────▶   │      │                     │
│        │ LLM  │    Action  t      │ Tool │                     │
│        │      │ ──────────────▶   │ exec │                     │
│        │      │                   │      │                     │
│        │      │    Observation t  │      │                     │
│        │      │ ◀──────────────   │      │                     │
│        └──┬───┘                   └──────┘                     │
│           │                                                    │
│           │ append (thought_t, action_t, observation_t)        │
│           │ to trace                                           │
│           ▼                                                    │
│        [           trace                ]                      │
│           │                                                    │
│           └───── feeds back into LLM at step t+1 ────┐         │
│                                                      ▼         │
│                                                 loop or        │
│                                                 Finish[]       │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

What matters about that picture:

The LLM is stateless. The trace is the state. Every forward pass is a fresh load of context. Thoughts are introspection. Actions are extrospection. They alternate by design, and neither one alone is enough. Observations come from outside the model. They are the ground truth that disciplines the reasoning. Termination is a model decision (`Finish`), bounded by an orchestrator-imposed step budget.
