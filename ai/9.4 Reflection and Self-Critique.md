## The Problem Reflection Is Trying to Solve

Before introducing the technique, the motivation has to land. Otherwise reflection looks like a clever trick rather than a structural fix for something broken.

A vanilla LLM call is a *one-shot commitment*. The model reads the prompt, runs a single forward pass through its weights, and emits tokens. There is no built-in moment where it stops, looks at what it produced, and decides whether the output is actually any good. Whatever comes out is the answer. If it is wrong, it is wrong with the same confident cadence as when it is right.

This becomes pathological the moment you put an LLM inside an agent loop. Consider a ReAct-style trajectory:

```
Thought_1 -> Action_1 -> Observation_1
Thought_2 -> Action_2 -> Observation_2
Thought_3 -> Action_3 -> Observation_3
...
```

A bad `Thought_1` poisons every step downstream. The model conditions on its own prior reasoning, so once it has committed to "the bug is in the auth middleware," every subsequent observation gets interpreted through that lens. Errors do not just persist. They *compound*. Yao et al. observed this directly in the ReAct paper: trajectories often fail because the agent locks onto a wrong hypothesis early and never escapes it.

Now contrast this with how a human writes a difficult email, debugs a tricky function, or proves a non-trivial theorem. Nobody does it in one shot. The actual cognitive loop looks like:

1. Produce a candidate answer.
2. Step back and look at it critically. "Wait, this doesn't handle the empty case."
3. Revise.
4. Repeat until satisfied.

Reflection patterns are the agent-architecture answer to this gap. They give the model a structured opportunity to look at its own work *before* the work becomes load-bearing for the next step.

## The Core Pattern: Act -> Critique -> Revise

Strip away the paper-specific machinery and every reflection technique reduces to the same three-stage loop:

```
+----------+      +-----------+      +----------+
|          |      |           |      |          |
|   ACT    | ---> | CRITIQUE  | ---> |  REVISE  |
|          |      |           |      |          |
+----------+      +-----------+      +----------+
     ^                                     |
     |                                     |
     +-------------------------------------+
              (until stopping condition)
```

Three roles execute in sequence, possibly by the same underlying model wearing different "hats":

- **Actor** produces a candidate output (an answer, a piece of code, a plan, an action).
- **Critic** examines the candidate and produces *feedback*: what is wrong, what is missing, what could be better.
- **Refiner** consumes the original candidate plus the feedback and produces a new candidate.

The loop terminates on some condition: the critic says "good enough," a budget is exhausted, or quality stops improving.

The reason this three-stage structure matters, and why you cannot collapse it into "just tell the model to do better" in one prompt, is that role separation creates productive distance. When the model is asked to *generate*, it optimizes for fluent continuation. When the model is asked to *critique a fixed artifact*, it optimizes for finding flaws. These are different objectives, and giving them different contexts produces measurably different outputs from the same weights. The critic stage is not just a re-roll. It is a *different mode of computation* over the same artifact.

That is the structural insight under every reflection paper. The rest is implementation detail.

## Self-Refine: Single Model, Three Hats

The cleanest instantiation of the pattern is **Self-Refine**. It uses one model, three prompts, and a loop.

The algorithm:

```
INPUT:  task x, model M, max iterations T
OUTPUT: refined answer y

y_0 = M(prompt_generate(x))           // initial answer
for t = 1 to T:
    fb_t = M(prompt_feedback(x, y_{t-1}))   // critique
    if fb_t indicates "stop":
        return y_{t-1}
    y_t = M(prompt_refine(x, y_{t-1}, fb_t)) // revise
return y_T
```

Three prompts power this:

- **`prompt_generate`**: "Given the task, produce an answer."
- **`prompt_feedback`**: "Given the task and this answer, identify specific issues. Be precise about what is wrong and why."
- **`prompt_refine`**: "Given the task, the previous answer, and this feedback, produce an improved answer that addresses the feedback."

Here is what this looks like in TypeScript. Note the deliberate separation into pure functions that each take their own focused context:

```typescript
type Task = { description: string; constraints?: ReadonlyArray<string> };
type Feedback = { issues: ReadonlyArray<string>; done: boolean };
type RefineConfig = { maxIterations: number; model: LlmClient };

type LlmClient = {
    complete: (prompt: string) => Promise<string>;
    completeJson: <T>(prompt: string) => Promise<T>;
};

const buildGeneratePrompt = (task: Task): string =>
    `Task: ${task.description}\n` +
    `Constraints: ${task.constraints?.join("; ") ?? "none"}\n` +
    `Produce your best answer.`;

const buildFeedbackPrompt = (task: Task, candidate: string): string =>
    `Task: ${task.description}\n` +
    `Candidate answer:\n${candidate}\n\n` +
    `Critique this candidate. Identify concrete issues: errors, ` +
    `omissions, weaknesses. If the candidate is already correct ` +
    `and complete, set "done": true. ` +
    `Respond as JSON: { "issues": string[], "done": boolean }`;

const buildRefinePrompt = (
    task: Task,
    candidate: string,
    feedback: Feedback,
): string =>
    `Task: ${task.description}\n` +
    `Previous answer:\n${candidate}\n\n` +
    `Feedback to address:\n${feedback.issues.map((i, n) => `${n + 1}. ${i}`).join("\n")}\n\n` +
    `Produce a revised answer that addresses each piece of feedback.`;

const selfRefine = async (
    task: Task,
    config: RefineConfig,
): Promise<string> => {
    const { model, maxIterations } = config;
    const initial = await model.complete(buildGeneratePrompt(task));

    // Mutable accumulator is intentional: tight loop, avoid allocation.
    let current = initial;
    for (let i = 0; i < maxIterations; i++) {
        const feedback = await model.completeJson<Feedback>(
            buildFeedbackPrompt(task, current),
        );
        if (feedback.done || feedback.issues.length === 0) {
            return current;
        }
        current = await model.complete(
            buildRefinePrompt(task, current, feedback),
        );
    }
    return current;
};
```

The `let` and `for` are the kind of place the preference list explicitly permits: a hot loop with a single accumulator where reassignment avoids allocating a chain of intermediate bindings.

**What Self-Refine demonstrates empirically.** Madaan et al. reported gains across diverse tasks (math word problems, code optimization, dialogue response generation) using only the model's ability to critique its own output. No fine-tuning required, no external supervision, no extra labels. The mechanism is purely prompt-level role separation.

**Where Self-Refine fails.** This is the part papers tend to underweight and Anthropic's "Building Effective Agents" flags directly. The critic is the same model that generated the candidate, running on similar context. If the model has a *systematic* blind spot, say it consistently misunderstands a particular API or a particular kind of edge case, the critic will share that blind spot. Self-Refine improves *fluency-class* errors (the model knew better but didn't slow down) far better than *knowledge-class* errors (the model genuinely doesn't know). You will also see *sycophantic critique*: the critic says "looks good!" when the answer is wrong, because the candidate is in-context and the model is pattern-matching on "approval" continuations.

## Reflexion: Reflection as Verbal Reinforcement Learning

Self-Refine is single-trajectory: critique and revise *this* answer. **Reflexion** generalizes the pattern across *multiple trajectories* on the same task, and reframes the whole thing in reinforcement-learning vocabulary.

The setup is an agent attempting a task with a verifiable outcome (the test suite passes, the answer matches ground truth, the game is won). Reflexion runs the agent end-to-end, observes whether it succeeded, and if it failed, asks the model to produce a *verbal reflection* on why. The reflection is a few sentences of self-diagnosis. That reflection text is stored in an **episodic memory**, and on the next attempt the agent sees its prior reflections as part of its context.

The architecture has three named components:

```
+-------------------+   action   +------------+
|                   | ---------> |            |
|     ACTOR (M_a)   |            |   ENV      |
|                   | <--------- |            |
+-------------------+ observation+------------+
        ^                              |
        |                              | trajectory
        |                              v
        |                       +--------------+
        |                       |              |
        |                       | EVALUATOR    |
        |                       |    (M_e)     |
        |                       +--------------+
        |                              |
        |                              | reward / outcome
        |                              v
        |   reflection text     +------------------+
        +---------------------- |                  |
                                | SELF-REFLECTION  |
                                |     (M_sr)       |
                                +------------------+
                                          ^
                                          |
                                  +---------------+
                                  |  EPISODIC MEM |
                                  +---------------+
```

- **Actor** $M_a$: generates the trajectory of actions in the environment, conditioned on the task and any prior reflections in memory.
- **Evaluator** $M_e$: produces a scalar reward signal. This can come from the environment (test passes/fails), an external model, or even the model itself prompted to score the trajectory.
- **Self-Reflection** $M_{sr}$: given a failed trajectory and its reward, produces a textual reflection. The reflection is a hypothesis about what went wrong and how to do better next time.
- **Episodic memory**: accumulates reflections across attempts. The actor sees them on subsequent trials.

The "verbal RL" framing is the conceptual centerpiece. In standard policy-gradient RL, after a failed episode you update the policy parameters $\theta$ via gradients of the form:

$$\nabla_\theta J(\theta) = \mathbb{E}_\tau\left[\sum_t \nabla_\theta \log \pi_\theta(a_t \mid s_t) \cdot R(\tau)\right]$$

Reflexion proposes a *language-space analog*. The "policy update" is not a gradient step on weights. It is *a paragraph of natural language added to the context*. The next trajectory uses the same weights but sees that paragraph, and the paragraph functions as a localized policy modification: "last time you tried X and it failed because Y, so this time try Z."

This is a striking idea because it sidesteps gradient-based learning entirely. The model's weights never change. What changes is the conditioning text. Because LLMs are powerful in-context learners, a well-formed reflection produces behavior on trial $t+1$ that is meaningfully different from trial $t$. Sometimes the difference is dramatic.

A simplified Reflexion loop in TypeScript:

```typescript
type Trajectory = {
    actions: ReadonlyArray<string>;
    observations: ReadonlyArray<string>;
    finalOutput: string;
};

type Outcome = { success: boolean; reward: number; details: string };

type ReflexionConfig = {
    maxTrials: number;
    actor: (task: string, memory: ReadonlyArray<string>) => Promise<Trajectory>;
    evaluator: (task: string, trajectory: Trajectory) => Promise<Outcome>;
    reflector: (
        task: string,
        trajectory: Trajectory,
        outcome: Outcome,
    ) => Promise<string>;
};

const runReflexion = async (
    task: string,
    config: ReflexionConfig,
): Promise<{ trajectory: Trajectory; outcome: Outcome; trials: number }> => {
    const memory: Array<string> = [];

    for (let trial = 0; trial < config.maxTrials; trial++) {
        const trajectory = await config.actor(task, memory);
        const outcome = await config.evaluator(task, trajectory);

        if (outcome.success) {
            return { trajectory, outcome, trials: trial + 1 };
        }

        // Verbal "policy update": append a reflection to episodic memory.
        const reflection = await config.reflector(task, trajectory, outcome);
        memory.push(reflection);
    }

    // Final attempt's results returned if budget exhausted.
    const finalTrajectory = await config.actor(task, memory);
    const finalOutcome = await config.evaluator(task, finalTrajectory);
    return {
        trajectory: finalTrajectory,
        outcome: finalOutcome,
        trials: config.maxTrials + 1,
    };
};
```

Reflexion's reported results were strongest on tasks where the outcome is *verifiable*: coding benchmarks (HumanEval, MBPP), decision-making tasks with clear success criteria, knowledge-intensive QA with answer-checking. The verifiability matters because it grounds the reflection. The reflector knows for certain that the previous trial failed, so it does not need to negotiate with itself about whether revision is warranted. Contrast this with Self-Refine, which has to *decide* whether the current answer is good. That is a much harder judgment call.

## Critic Models: When the Critic Is Not the Actor

Self-Refine and Reflexion both have the actor and critic share weights. A natural extension is **using a different model as the critic**, and this opens a design space worth understanding.

**Why use a separate critic at all?** Because the shared-blind-spot problem from Self-Refine is real. If the actor consistently makes a particular class of error, asking the same model to spot that error is statistically unfavorable. Same training data, same biases, same priors. A different model brings different priors. A *trained* critic brings priors that were specifically optimized for detecting errors.

The design space breaks down along two axes:

|                    | **Same model as actor** | **Different model**           |
| ------------------ | ----------------------- | ----------------------------- |
| **Prompted**       | Self-Refine             | "Big model critiques small"   |
| **Trained/Tuned**  | Process reward models on the same base | Specialized verifier models   |

A few notable points in this space:

**CRITIC** augments self-critique with *tools*. Rather than asking the model "is this answer correct?", CRITIC asks the model to *use tools* to check. Run the code. Query a search engine. Do the calculation. The critic is still the same LLM, but its judgment is grounded in tool output rather than its own forward pass. This addresses the sycophancy problem directly. The model is not asked to second-guess itself. It is asked to *check*.

**Process Reward Models (PRMs)** are trained critics. They are typically smaller models fine-tuned to assign a quality score to each step of a reasoning trajectory. Lightman et al. showed that step-by-step process supervision outperforms outcome-only supervision for math reasoning. The conceptual move here is that the critic is no longer just "is the final answer right?" but "is *this intermediate step* a reasonable thing to do?" This dense feedback signal is much more useful for revision.

**Verifier-guided search** (the variant where a critic ranks $k$ candidate completions and picks the best) is structurally similar to reflection but operates over parallel candidates instead of a serial revise loop. This is the bridge between reflection and **Tree of Thoughts**. ToT runs explicit search over a tree of reasoning steps, with a critic/evaluator pruning branches. Reflection is the linear-search variant of the same family. ToT is the breadth-search variant.

A pragmatic TypeScript skeleton showing the separate-critic pattern:

```typescript
type Candidate = { content: string; meta: Record<string, unknown> };
type Critique = { score: number; issues: ReadonlyArray<string>; suggestions: ReadonlyArray<string> };

type ActCritiqueReviseConfig = {
    actor: LlmClient;       // potentially capable, expensive
    critic: LlmClient;      // potentially specialized, possibly different model
    qualityThreshold: number;
    maxIterations: number;
};

const actCritiqueRevise = async (
    task: Task,
    config: ActCritiqueReviseConfig,
): Promise<Candidate> => {
    const { actor, critic, qualityThreshold, maxIterations } = config;

    let candidate: Candidate = {
        content: await actor.complete(buildGeneratePrompt(task)),
        meta: { iteration: 0 },
    };

    for (let i = 1; i <= maxIterations; i++) {
        const critique = await critic.completeJson<Critique>(
            buildCriticPrompt(task, candidate.content),
        );
        if (critique.score >= qualityThreshold) {
            return { ...candidate, meta: { ...candidate.meta, finalScore: critique.score } };
        }
        candidate = {
            content: await actor.complete(
                buildRevisePrompt(task, candidate.content, critique),
            ),
            meta: { iteration: i, lastScore: critique.score },
        };
    }
    return candidate;
};
```

Note that the actor and critic are now distinct `LlmClient` instances. In practice this might mean the actor is a frontier-class model and the critic is a smaller, cheaper, possibly task-tuned model. The economics often favor this split. Critique is sometimes easier than generation, so you can pay less for the critic and still get useful feedback.

## When Reflection Helps, When It Hurts

Reflection is not free, and a thoughtful agent designer needs to know the failure modes. Anthropic's "Building Effective Agents" (2024) is particularly direct on this: reflection adds latency and cost, and you should only reach for it when there is evidence it improves outcomes for *your* task.

**Reflection helps when:**

- The task has *verifiable* outcomes (tests pass, math checks out, schema validates). Verification grounds the critique and prevents drift.
- Errors are recoverable. The critic can spot them and the refiner can fix them within the model's capability envelope.
- The cost of being wrong exceeds the cost of additional model calls. Production code, legal language, anything where shipping a bad answer is expensive.
- The task allows for *partial* progress, so refinement compounds when each revision actually improves something.

**Reflection hurts (or wastes resources) when:**

- The model's first answer is already at the ceiling of its capability. Asking it to critique and revise just generates noise. Sometimes it generates *worse* noise, because the critic hallucinates problems where none exist and the refiner "fixes" things that were correct. This is a documented failure mode: revision quality can *decrease* monotonically after the first iteration if the underlying task is at capability ceiling.
- The critique loop is ungrounded. If neither the critic nor the refiner can verify anything, you are watching the model talk to itself, and the conversation has no anchor to reality.
- Sycophancy dominates. The critic agrees with whatever the actor produced. The output of an unaltered Self-Refine loop on a confident-but-wrong answer is often the same confident-but-wrong answer with more flowery language.
- The cost structure is wrong. If your task budget is one model call, reflection is not an option. If reflection costs $3\times$ the base call and yields a $5\%$ quality improvement on a low-stakes task, that is a bad trade.
- The stopping criterion is bad. Without a principled stop, you either burn budget on a fixed iteration cap or risk infinite loops of "almost there, one more revision."

The stopping criterion is worth dwelling on. The options, roughly ordered by reliability:

| Stopping criterion                               | Reliability      | Cost            |
| ------------------------------------------------ | ---------------- | --------------- |
| External verifier passes (tests pass, schema OK) | High             | Verifier cost   |
| Quality plateau (score stops improving)          | Medium           | Multiple iters  |
| Self-judgment "done" (critic says good enough)   | Low (sycophancy) | One critic call |
| Fixed iteration count                            | Predictable      | Always max      |

A pattern that works well in practice: combine an external verifier (when available) with a fixed-iteration ceiling. The verifier short-circuits the loop the moment it can; the ceiling prevents runaway cost on hard cases.

## How Reflection Composes with Other Patterns

Reflection is not a standalone architecture. It is a building block that slots into larger agent designs.

**Reflection + ReAct.** Within a ReAct trajectory, you can insert a critique step after each action or at the end of the trajectory. The latter is Reflexion. The former is more aggressive: every action gets a "should I really take this action?" gate. Higher quality, higher cost.

**Reflection + Tree of Thoughts.** ToT is reflection generalized to a tree. You produce $k$ candidates per step, evaluate them (the critic role), and expand the best ones. Reflection is the special case where $k=1$ and the tree is a linear chain.

**Reflection + planning.** A planner produces a plan, a critic examines the plan, the planner revises. This catches plan-level errors before the agent commits to executing the plan. Particularly valuable when execution is expensive or irreversible.

**Reflection + multi-agent.** The actor and critic can be entirely separate agents with separate prompts, tools, and even separate models. This is sometimes called "debate" or "actor-critic" agent architecture. The benefit is stronger role separation. The cost is orchestration complexity.

## The Mental Model to Walk Away With

The pattern is structurally simple: produce, examine, revise. The conceptual depth lies in three claims that took the field a few years to internalize.

The first claim is that role separation is real computation. Asking the same model to generate versus to critique produces different outputs, not because of any architectural difference, but because the conditioning context changes the model's effective objective. Reflection is, at its core, an exploitation of this fact.

The second claim is that language can substitute for gradients. Reflexion's "verbal RL" framing is more than a metaphor. Natural-language reflections, when added to context, function as in-place policy modifications for in-context learners. You get policy improvement without any weight updates.

The third claim is that the critic's grounding is the system's ceiling. Self-critique with no external signal is fundamentally limited by the model's own self-knowledge. Tool-grounded critique raises the ceiling. So does verifier-grounded critique. So does process-supervised critique. Each of these works by injecting information the actor did not have. Where you place the critique's anchor determines what kinds of errors the loop can actually catch. The anchor could sit in the model, in a tool, in a verifier, or in an external evaluator.
