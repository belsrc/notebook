## The single-agent baseline (so we know what we're trying to beat)

Before adding agents, you need to be precise about what a single agent already does. The ReAct loop is the substrate every multi-agent pattern is built on:

```
                              ┌──────────────────────────┐
                              │  System / Task prompt    │
                              └─────────────┬────────────┘
                                            ↓
        ┌──────────────────────┐    ┌──────────────────────┐
        │     Observation      │ →  │       Thought        │
        │  (tool result, env   │    │  (reason, plan next  │
        │   feedback, error)   │    │   step, self-check)  │
        └──────────────────────┘    └──────────┬───────────┘
                  ↑                            ↓
                  │                  ┌──────────────────────┐
                  └──────────────────┤        Action        │
                                     │  (tool call, query,  │
                                     │   final answer)      │
                                     └──────────────────────┘
```

A single ReAct agent has three structural properties to keep in mind, because every multi-agent decision will be a trade against one of them:

1. One context window. All thoughts, observations, and tool outputs accumulate in the same KV cache. The context grows monotonically, and at roughly 200K tokens (current frontier models) it must be truncated, summarized, or externalized.
2. One perspective. The same prompt, the same role, the same biases on every step. There is no internal "second opinion."
3. Sequential execution. Step $n+1$ depends on the observation from step $n$. The loop itself cannot be parallelized.

Two well-known refinements stretch the single-agent design before you need to reach for multiple agents. Reach for them first, because they are cheaper:

- Reflexion (Shinn et al., 2023): after a failed trajectory, the agent writes a verbal self-critique into a persistent memory buffer and retries. Still one agent, but it gets a second pass at the task with hindsight. Shinn et al. showed this improved success rates on HotPotQA, AlfWorld, and HumanEval coding tasks without any weight updates.
- Tree of Thoughts (ToT) (Yao et al., 2023): the agent expands multiple candidate "thoughts" at each step and uses a search procedure (BFS or DFS) with a value-estimator prompt to prune branches. On Game-of-24, this lifted GPT-4 from roughly 4% (CoT) to 74% solve rate.

What these two do is different. Reflexion adds temporal diversity (different attempts). ToT adds spatial diversity (different branches). Both can be done with one model and one tool harness. If your problem only needs more diversity of thought, you probably do not need multi-agent at all. ToT or Reflexion may suffice at a fraction of the cost.

Multi-agent systems are what you reach for when the structural limits actually bind: one context window, one perspective, one execution thread.

## The pressure points that motivate going multi-agent

A useful exercise before reading the patterns is to predict what kind of task would push you past each of the three single-agent limits.

| Limit binding                       | What that feels like in practice                                              | What pattern relieves it                |
| ----------------------------------- | ----------------------------------------------------------------------------- | --------------------------------------- |
| Context window saturation           | "Read these 40 papers and synthesize." Even with summarization, you run out. | Orchestrator-worker (parallel CWs)      |
| Single perspective / blind spots    | Factual claims that need challenge; reasoning that needs adversarial pressure | Debate                                  |
| Sequential bottleneck on breadth    | Many independent leads to chase ("research the 12 competitors in this space") | Orchestrator-worker (parallel time)     |
| Distinct skill profiles per subtask | A workflow with naturally separable roles (spec, design, code, test)          | Role-specialized pipeline               |

Anthropic frames the underlying trade explicitly. From their multi-agent research write-up: *"Multi-agent systems use about 15× more tokens than chat interactions"* and *"token usage alone explains 80% of performance variance"* on their BrowseComp evaluation (Anthropic, *How we built our multi-agent research system*, 2025). Their internal evaluation showed a 90.2% performance improvement of a multi-agent system (Opus 4 lead with Sonnet 4 subagents) over single-agent Opus 4 on research tasks. Those two numbers, 15× cost and 90% gain, are the lens through which every multi-agent design decision should be filtered. If the gain does not justify the 15×, you are burning tokens.

## Pattern 1: orchestrator-worker

This is the workhorse of production multi-agent systems, and the only pattern Anthropic explicitly named in *Building Effective Agents* under "workflows": *"In the orchestrator-workers workflow, a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results"* (Anthropic, 2024).

### Shape

```
                       ┌──────────────────────────┐
                       │       Orchestrator       │
                       │      (Lead Agent)        │
                       │                          │
                       │  1. Decompose query      │
                       │  2. Dispatch subtasks    │
                       │  3. Wait for results     │
                       │  4. Synthesize answer    │
                       └────┬───────┬───────┬─────┘
                  spawn     │       │       │   spawn
                ┌───────────┘       │       └───────────┐
                ↓                   ↓                   ↓
          ┌──────────┐        ┌──────────┐        ┌──────────┐
          │ Worker A │        │ Worker B │        │ Worker C │
          │  fresh   │        │  fresh   │        │  fresh   │
          │ context  │        │ context  │        │ context  │
          │  + tools │        │  + tools │        │  + tools │
          └────┬─────┘        └────┬─────┘        └────┬─────┘
               │                   │                   │
            findings            findings            findings
               └───────────────────┼───────────────────┘
                                   ↓
                       ┌──────────────────────────┐
                       │   Synthesis (by Lead)    │
                       │   → final answer +       │
                       │     citations            │
                       └──────────────────────────┘
```

### What makes this pattern work

Three engineering details turn the diagram into a real system:

1. Fresh context per worker. Each worker starts with an empty context window and receives only the focused subtask description. This is not an optimization. It is the entire reason the pattern beats a single agent on breadth-first work. You are buying $n$ independent context windows in parallel.
2. Lossy aggregation. Workers return compressed findings, not their full trajectory. The lead sees a summary, not 200K tokens of intermediate tool calls. Without this compression, the orchestrator's context dies first.
3. Externalized state. Anthropic's research system has the lead agent write its plan to a memory store before dispatching, so a context truncation does not lose the plan (Anthropic, 2025). Workers also persist artifacts to a filesystem and return references, not contents.

### Minimal implementation

```typescript
type SubTask = Readonly<{
  id: string;
  description: string;
  context: string;
}>;

type SubTaskResult = Readonly<{
  id: string;
  findings: string;
  citations: ReadonlyArray<string>;
}>;

type LLMCall = (system: string, user: string) => Promise<string>;

// 1. Orchestrator decomposes the top-level query.
const planSubTasks = async (
  llm: LLMCall,
  query: string,
): Promise<ReadonlyArray<SubTask>> => {
  const planJson = await llm(
    "You are the lead researcher. Decompose the user query into 2-5 " +
      "INDEPENDENT, parallelizable subtasks. Each subtask must be " +
      "self-contained and solvable without seeing the others. Return JSON " +
      "array of {id, description, context}.",
    query,
  );
  return JSON.parse(planJson) as ReadonlyArray<SubTask>;
};

// 2. Each worker runs on a fresh context window with one focused subtask.
const runWorker = async (
  llm: LLMCall,
  task: SubTask,
): Promise<SubTaskResult> => {
  const findings = await llm(
    "You are a research subagent. Investigate the assigned subtask using " +
      "your tools. Return CONCISE findings (~500 tokens) with citations. " +
      "Do not include intermediate reasoning.",
    JSON.stringify(task),
  );
  return { id: task.id, findings, citations: [] };
};

// 3. Orchestrator synthesizes worker outputs into one answer.
const synthesize = async (
  llm: LLMCall,
  query: string,
  results: ReadonlyArray<SubTaskResult>,
): Promise<string> =>
  llm(
    "You are the lead researcher. Synthesize the subagent findings into a " +
      "coherent answer to the original query. Preserve citations. Note any " +
      "contradictions between subagents.",
    JSON.stringify({ query, results }),
  );

// 4. Top-level: plan, dispatch in parallel, synthesize.
const runOrchestratorWorker = async (
  llm: LLMCall,
  query: string,
): Promise<string> => {
  const tasks = await planSubTasks(llm, query);
  const results = await Promise.all(tasks.map((t) => runWorker(llm, t)));
  return synthesize(llm, query, results);
};
```

Three things in the code are worth attention:

- The `Promise.all` is doing the real work. It is the parallel context window mechanism in JavaScript form. If you serialize this, you lose half the value.
- The `synthesize` system prompt is explicit about contradictions. A common failure mode is the orchestrator silently averaging contradictory worker outputs into a confidently wrong answer.
- The worker's system prompt budgets its output. Without this, workers happily dump 8K tokens each into the orchestrator's context.

### The cost model

Let $T_{\text{chat}}$ be the tokens used by a single-turn chat for the same surface task, $n$ the number of subagents, and $\alpha$ the worker overhead ratio (typically ~4× per Anthropic, because each worker also runs a ReAct loop with tool calls). Then:

$$T_{\text{multi}} \approx T_{\text{plan}} + n \cdot \alpha \cdot T_{\text{chat,subtask}} + T_{\text{synth}}$$

For Anthropic's research system this lands near $15 \cdot T_{\text{chat}}$. So the orchestrator-worker pattern is correct only when the task value exceeds 15× a chat interaction's cost. For a one-shot research question worth a human-hour (about \$50 of labor), that bar is trivially cleared. For a customer-support tier-1 deflection task worth about \$0.10, it is not.

### Where it works and where it does not

It works for:

- Breadth-first research (Anthropic's canonical use case).
- Multi-document analysis with independent documents.
- Codebase-wide refactors where subtasks decompose by file or module.
- Competitive-intelligence sweeps ("profile these 12 companies").

It fails for:

- Tasks with tight coupling between subtasks. Anthropic is explicit: *"domains that require all agents to share the same context or involve many dependencies between agents are not a good fit for multi-agent systems today"* (Anthropic, 2025).
- Most coding tasks. The same source notes that coding is mostly not parallelizable, which is why Claude Code's primary loop is single-agent with subagents only as a tool when truly parallel work appears.
- Anything where the orchestrator's decomposition is itself the hard part. If the lead cannot write a clean subtask spec, the workers run off cliffs in parallel.

## Pattern 2: debate

The orchestrator-worker pattern uses multiple agents to cover more ground. Debate uses multiple agents to cover the same ground from different angles, with the explicit goal of catching errors that any one agent would commit.

### Shape

```
                    Question
                       │
                       ↓
        ┌──────────────────────────────────┐
        │  Round 1                         │
        │    Agent A → answer A₁           │
        │    Agent B → answer B₁           │
        │  (each produced independently)   │
        └──────────────┬───────────────────┘
                       │ exchange transcripts
                       ↓
        ┌──────────────────────────────────┐
        │  Round 2                         │
        │    Agent A sees B₁  → A₂         │
        │    Agent B sees A₁  → B₂         │
        │  (each may revise or hold firm)  │
        └──────────────┬───────────────────┘
                       │
                       ... repeat k rounds
                       │
                       ↓
              ┌─────────────────┐
              │  Judge agent OR │
              │  convergence    │
              │  detection      │
              └─────────────────┘
```

### Why this works (and when it does not)

The intuition: a single agent's hallucinations and biases are correlated within its own trajectory, but largely uncorrelated across independent agents on the same question (Du et al., *Improving Factuality and Reasoning in Language Models through Multiagent Debate*, 2023). Forcing them to reconcile surfaces the error. This is the same logic that makes ensemble methods work in classical ML, recast for LLMs.

The catch, and the reason debate is not always better, is that LLMs are often sycophantic. If Agent A states a confident wrong answer first, Agent B may capitulate rather than holding ground. Mitigations:

- Have all agents produce Round 1 simultaneously (no peek).
- Use temperature or sampling diversity between agents.
- Assign Agent B an explicit "skeptical" role.
- Add a separate judge agent that does not produce its own answer until after $k$ rounds.

### Sketch

```typescript
type DebateRound = Readonly<{
  agentId: string;
  argument: string;
}>;

const runDebateRound = async (
  llm: LLMCall,
  agentId: string,
  question: string,
  priorRounds: ReadonlyArray<DebateRound>,
): Promise<DebateRound> => {
  const argument = await llm(
    `You are agent ${agentId}. Defend your position on the question. ` +
      "Consider arguments from other agents. Revise ONLY if their evidence " +
      "is genuinely stronger; otherwise hold firm and explain why.",
    JSON.stringify({ question, priorRounds }),
  );
  return { agentId, argument };
};

const debateLoop = async (
  llm: LLMCall,
  question: string,
  agentIds: ReadonlyArray<string>,
  roundsRemaining: number,
  history: ReadonlyArray<DebateRound>,
): Promise<ReadonlyArray<DebateRound>> => {
  if (roundsRemaining === 0) return history;
  // Round-level parallelism: agents in the same round speak independently.
  const newRound = await Promise.all(
    agentIds.map((id) => runDebateRound(llm, id, question, history)),
  );
  return debateLoop(
    llm,
    question,
    agentIds,
    roundsRemaining - 1,
    [...history, ...newRound],
  );
};

const runDebate = async (
  llm: LLMCall,
  question: string,
  agentIds: ReadonlyArray<string>,
  rounds: number,
): Promise<string> => {
  const transcript = await debateLoop(llm, question, agentIds, rounds, []);
  return llm(
    "You are an impartial judge. Decide the strongest answer based on the " +
      "arguments and evidence. Do not defer to majority; weigh evidence.",
    JSON.stringify({ question, transcript }),
  );
};
```

### Where it works and where it does not

It works for:

- Fact-checking and claims that benefit from adversarial review.
- Mathematical or logical reasoning where errors are subtle but verifiable.
- Decisions where you want a "red team" perspective as a built-in feature.

It fails for:

- Anything that already has a deterministic verifier. Just run the verifier.
- Open-ended generation. Debate tends to regress to bland consensus.
- High-volume, low-stakes queries. The $n \cdot k$ token multiplier is brutal.

A useful heuristic: if you can write a unit test for the answer, prefer evaluator-optimizer over debate. Debate is for cases where the "test" is itself argumentative.

## Pattern 3: role-specialized agents

This pattern goes by many names: role-playing, agentic workflow, pipeline-of-agents. It is associated with frameworks like CAMEL (Li et al., 2023), MetaGPT (Hong et al., 2023), and AutoGen. The idea: give each agent a different system prompt encoding a different role, and chain them.

### Shape

```
   ┌───────────┐    ┌───────────┐    ┌───────────┐    ┌───────────┐
   │  Product  │ →  │ Architect │ →  │   Coder   │ →  │  Tester   │
   │  Manager  │    │           │    │           │    │           │
   │   (PRD)   │    │ (design)  │    │  (code)   │    │ (verify)  │
   └─────┬─────┘    └─────┬─────┘    └─────┬─────┘    └─────┬─────┘
         │                │                │                │
         └────────────────┴────────────────┴────────────────┘
                       feedback loops (optional)
```

Each box is an agent with a different persona, different tools, and often a different model size. The output of one feeds the input of the next.

### Why role specialization is suspicious

Role-specialized pipelines are the most over-applied multi-agent pattern in the wild. Hold them to a higher bar of skepticism than the other two. Here is why.

Modern frontier models can switch personas within a single context. A single Claude call instructed to "first act as a PM and write a PRD, then as an architect and design the system, then as a coder..." will often outperform four separate agent calls, because the same model has access to the full reasoning trail of every prior step, with no information loss in the handoff.

The argument for the multi-agent version is information-theoretic: by forcing a handoff through a structured artifact (a PRD document, a design doc, a code file), you compel each stage to externalize its thinking. This is the same logic as code review by a different person. The act of communicating exposes assumptions. It is a legitimate gain, but it is a smaller gain than people assume.

The argument against: every handoff is lossy. The architect agent only sees the PRD, not the PM's deliberations. If the PRD is ambiguous, the architect cannot ask the PM the way a human would; it just makes assumptions. Errors compound through the pipeline.

### When it actually earns its place

Role-specialized pipelines are correct when one or more of these conditions holds:

1. The roles have genuinely different tool sets. Your PM agent has access to a market-research database; your coder has a sandboxed code interpreter; your tester has a CI runner. Different tools is a real reason for different agents, because each tool's API surface bloats the prompt.
2. The roles have genuinely different model needs. A cheap small model can do the test-running; a frontier model writes the architecture. This is where specialization saves money rather than spending it.
3. The handoff artifact is a deliverable in its own right. If the PRD itself is a document a human needs to review, then producing it as a clean standalone output is valuable independent of code quality.

If none of these three hold, you probably want a single agent with a structured prompt.

## The decision framework: when to use which (or none)

Anthropic's *Building Effective Agents* essay is unusually direct on this: *"When building applications with LLMs, we recommend finding the simplest solution possible, and only increasing complexity when needed. This might mean not building agentic systems at all."* (Anthropic, 2024).

Here is the decision tree as I find it useful to walk through it:

```
                    Is the task solvable by one prompt?
                                 │
                          ┌──────┴──────┐
                         YES            NO
                          │              │
                  STOP. Single prompt.   │
                                         ↓
                       Does the task need tools or
                          multi-step reasoning?
                                 │
                          ┌──────┴──────┐
                         NO            YES
                          │              │
                  Use a workflow         │
                  (chain / route).       ↓
                                  Can the agent succeed
                                  with one ReAct loop?
                                         │
                                  ┌──────┴──────┐
                                 YES            NO
                                  │              │
                           Single ReAct agent.   │
                           Add Reflexion if      │
                           failures are common.  ↓
                                          Is the bottleneck
                                          BREADTH or DEPTH?
                                                 │
                                       ┌─────────┴─────────┐
                                     BREADTH              DEPTH
                                  (many parallel    (one hard answer
                                  independent leads) needing scrutiny)
                                       │                  │
                                       ↓                  ↓
                                 Orchestrator-       Debate, or
                                 worker.             evaluator-optimizer
                                                     (single-agent loop
                                                     with critic).

                                  Do roles have distinct
                                  tools, models, or artifacts?
                                       │
                                  ┌────┴────┐
                                 YES        NO
                                  │          │
                          Role-specialized   │
                          pipeline.          ↓
                                       Don't role-split.
                                       Single agent with
                                       structured prompt.
```

Three trip-wires that should make you stop and reconsider:

1. The 15× test. If the task value is less than $15 \times$ a single-shot chat cost, multi-agent is wrong. Period.
2. The decomposability test. If you cannot write the worker-task specifications yourself in 30 seconds, the orchestrator probably cannot either. Subtle decomposition is the actual hard problem; once you can decompose, parallel execution is easy.
3. The coupling test. If subtasks need to see each other's intermediate state, you do not have parallel subtasks. You have a single sequential task pretending to be parallel.

## When multi-agent earns its keep

Concrete signals that the pattern is right for your task:

- The task has an explicit "and" structure. "Research X and Y and Z where each is independent."
- A human doing the task would assign it to multiple junior researchers in parallel.
- The expected output is a synthesis document, not a continuous trajectory.
- Tool calls inside subtasks are read-only against external state, so workers do not conflict.
- Latency matters and the parallel speedup is real. Five minutes of parallel research beats 25 minutes serial.
- The task's correctness can be verified after the fact, so debate's improvement is measurable.

## When it adds latency without value

Concrete signals that should kill the multi-agent design:

- Tight inter-subtask coupling. Subtask B needs the intermediate state of A, not just A's final output.
- Shared mutable state. Two workers both writing to a database, modifying the same file, or competing on a tool's rate limit.
- Latency-sensitive single-step decisions. A trading agent that must respond in 50 ms cannot afford an orchestrator round trip.
- Cheap tasks. Anything where token cost is more than ~10% of total task cost. The LLM is the bottleneck, not the human or the deliverable.
- Tasks where a deterministic verifier exists. Compilers, type checkers, unit tests, schema validators all beat debate. Run the verifier; do not debate.
- Tasks the model already solves at 95%+ in one shot. You are adding cost without ceiling to gain.
- Greenfield problems where you do not know what good looks like yet. Build single-agent first, measure, then consider multi-agent on the measured weaknesses.

A specific anti-pattern worth naming is the "agentic team-of-experts" landing-page pattern, where someone advertises a system with 7 named role-agents (CMO, CTO, Designer, Coder, Reviewer, and so on) running in a pipeline. Almost always, the same task is solved at higher quality and 1/10 the cost by a single Claude call with a well-structured prompt. The role-team has the appearance of organization, but the reality of lossy handoffs.

## Pitfalls in production systems

Six failure modes that the multi-agent literature underweights:

1. Error compounding. If each agent has a 95% step-success rate, a pipeline of 5 agents has $0.95^5 \approx 77\%$ overall success. With 10 agents, $\approx 60\%$. Pipelines degrade fast.
2. Citation laundering. A worker produces a finding with a weak citation. The orchestrator synthesizes the finding into a confident statement, dropping the qualifier. The final answer looks authoritative, but is not.
3. Coordination overhead at the protocol level. Async execution makes parallel speedups real, but introduces state-consistency, result-ordering, and partial-failure problems. Anthropic notes that even their team punted on async execution because *"result coordination, state consistency, and error propagation"* were too costly (Anthropic, 2025).
4. Non-determinism amplification. A single agent's nondeterminism is one source of variance. $n$ agents multiply it. Reproducing a failure becomes empirically harder, sometimes intractable.
5. Evaluation gets harder, not easier. With a single agent you can replay a trajectory. With multi-agent, you need per-agent logs, inter-agent message logs, and the synthesis step, all aligned. Observability tooling is mandatory, not optional.
6. Cost surprises. The 15× multiplier is on successful runs. Failed runs that hit retry logic can be 30× or more. Budgeting must be done with worst-case multipliers, not averages.

## Mental model: the minimum-viable agents principle

If I had to compress this module into one principle:

> Add agents only when each new agent makes a measurable improvement on a metric you have already defined. If you cannot name the metric, you cannot justify the agent.

This is the inverse of the prevailing trend in agent demos, which add agents to *look* sophisticated. The Anthropic essay's recommendation (start simple, add complexity only when measurement demands it) is the production-grade version of the same advice (Anthropic, 2024).

A useful visual to keep in your head:

```
   Capability gain
        ▲
        │                              ╭───── multi-agent
        │                         ╭────╯       (high cost, high gain,
        │                    ╭────╯             narrow applicability)
        │              ╭─────╯
        │         ╭────╯       evaluator-optimizer / debate
        │     ╭───╯
        │  ╭──╯                Reflexion / ToT
        │╭─╯
        │╯                     single ReAct agent
        │
        │                      structured single prompt
        │
        └────────────────────────────────────────────────►
                                                   Cost / complexity
```

The curve flattens. Every step up the ladder costs disproportionately more for the marginal gain. You earn the right to be on the next rung by exhausting the current one. That means you measured its failures and they are structural, not "the prompt could be better."
