## What Is a Token?

A token is the subword unit a language model processes, produced by Byte Pair Encoding (BPE). As a rule of thumb, one token is roughly four English characters or 0.75 words, though code, JSON, and non-Latin scripts tokenize less efficiently. For a full treatment of tokenization including content-type breakdowns, see [Context Window Mechanics](./Context%20Window%20Mechanics.md).

## How Tokens Map to Cost

API providers charge for LLM usage by counting the tokens that flow in and out of the model. This is measured in two buckets.

```
┌─────────────────────────────────────────────────────────────┐
│  A single API call                                          │
│                                                             │
│  ┌───────────────────────┐                                  │
│  │  INPUT TOKENS         │  Everything sent TO the model:   │
│  │  (a.k.a. prompt       │  - System prompt                 │
│  │   tokens)             │  - Conversation history          │
│  │                       │  - Your current message          │
│  └───────────────────────┘                                  │
│                                                             │
│  ┌───────────────────────┐                                  │
│  │  OUTPUT TOKENS        │  Everything generated BY the     │
│  │  (a.k.a. completion   │  model in its response           │
│  │   tokens)             │                                  │
│  └───────────────────────┘                                  │
│                                                             │
│  Total cost = (input tokens × input rate)                   │
│             + (output tokens × output rate)                 │
└─────────────────────────────────────────────────────────────┘
```

The exact rates vary per model and change over time, so always check the provider's pricing page directly. What matters architecturally is that **input and output are priced separately**, and the rates are almost never the same.

As a general pattern observed across major providers (OpenAI, Anthropic, Google):

- Output tokens are typically **3x to 5x more expensive** than input tokens for the same model tier.

This asymmetry exists because generating tokens is computationally heavier than reading them. During input processing, the model runs one forward pass over your entire prompt. During output generation, the model runs **one forward pass per token generated**, each time attending back to everything that came before. It is a fundamentally serial, accumulating workload.

## Why Verbose Prompts Are Not Free

Every word in your prompt is a small charge. That is easy to miss because prompts feel like "instructions you type once." But consider a real application:

```
┌─────────────────────────────────────────────────────────────┐
│  Chat application with a system prompt                      │
│                                                             │
│  System prompt:     800 tokens  (detailed persona + rules)  │
│  Conversation turn 1:  50 tokens in,  80 tokens out         │
│  Conversation turn 2: 130 tokens in, 120 tokens out         │
│    (turn 1 history now included in context)                 │
│  Conversation turn 3: 250 tokens in,  90 tokens out         │
│    (turns 1+2 history included)                             │
│                                                             │
│  The system prompt is re-sent with EVERY request.           │
│  It never "disappears" from the bill.                       │
└─────────────────────────────────────────────────────────────┘
```

In a multi-turn conversation, the system prompt and prior messages are concatenated into the prompt on every API call. This is because language models are **stateless**: they have no memory between calls. The application is responsible for replaying the history, and every replayed token is a billed input token.

The cost compounds in three ways:

**1. System prompt verbosity multiplies across every call.**

A 2,000-token system prompt that could have been written in 400 tokens wastes 1,600 tokens on every single request. Over 10,000 API calls, that is 16,000,000 unnecessary input tokens.

**2. Long conversation histories grow the input on every turn.**

By turn 20 of a conversation, even with short messages, the accumulated history can dwarf the new content being sent. Many applications mitigate this with a summarization or truncation strategy, but naive implementations pay the full price.

**3. Redundant context inflates without helping.**

Prompts that repeat the same instruction in multiple forms ("be concise", then "keep responses short", then "avoid long answers") do not improve model behavior proportionally to their token cost. The model's adherence to instructions is not additive with repetition.

Here is a concrete comparison:

```
┌──────────────────────────────────────────────────────────────────┐
│  VERBOSE PROMPT (237 tokens)                                     │
│  ──────────────────────────                                      │
│  "You are a highly intelligent assistant that always provides    │
│  thorough, detailed, well-reasoned responses. You must always    │
│  be polite, professional, and courteous. Never be rude. Always   │
│  format your responses clearly. Be helpful and accurate. Always  │
│  double-check your work before responding..."                    │
│                                                                  │
│  TIGHT PROMPT (41 tokens)                                        │
│  ─────────────────────────                                       │
│  "You are a professional assistant. Respond accurately and       │
│  clearly. Format output for readability."                        │
│                                                                  │
│  Difference: 196 tokens per call                                 │
│  At 100,000 calls: 19,600,000 wasted input tokens                │
└──────────────────────────────────────────────────────────────────┘
```

The tighter prompt will produce nearly identical output quality for most tasks. The verbose version has the illusion of being more precise, but it is mostly restating the model's defaults.

## How Output Length Affects Spend

Output length is where costs can truly surprise you, for two reasons: the higher per-token rate, and the fact that output length is often uncontrolled.

**Output tokens cost more per token than input tokens.** We covered the computational reason above. In practice this means a 500-token response to a 1,000-token prompt can cost more than the prompt itself, depending on the model.

**Output length is driven by the model's interpretation of what you want.**

If your prompt asks an open-ended question with no length guidance, the model will produce whatever length it deems complete. A question like "explain database indexing" could produce a 200-token response or a 2,000-token essay, depending on how the model reads the scope of the request.

This has direct spending implications:

```
┌──────────────────────────────────────────────────────────────────┐
│  Scenario: Summarization endpoint, 10,000 daily calls            │
│                                                                  │
│  Uncontrolled output: avg 600 tokens out per call                │
│    Daily output tokens:  6,000,000                               │
│                                                                  │
│  Controlled output ("Respond in 3 sentences or fewer"):          │
│    avg 80 tokens out per call                                    │
│    Daily output tokens:    800,000                               │
│                                                                  │
│  Reduction: 86% fewer output tokens                              │
│  Given output tokens cost ~4x input tokens, this is the         │
│  single highest-leverage optimization available.                 │
└──────────────────────────────────────────────────────────────────┘
```

**Chain-of-thought and reasoning modes amplify this further.**

Many modern models support an extended "thinking" or "reasoning" mode where the model works through a problem step-by-step before producing a final answer. These internal reasoning steps are themselves tokens, and they are billed accordingly. A reasoning trace for a complex problem can add 1,000 to 5,000 tokens to the output cost of a single call. This mode is worth it when accuracy on hard problems matters, but it is not free, and it should not be enabled by default across an application.

## The Full Picture

Every API call has the following cost structure:

```
┌──────────────────────────────────────────────────────────────────┐
│  INPUT TOKEN SOURCES (charged at input rate)                     │
│  ─────────────────────────────────────────                       │
│  System prompt             (static, paid every call)             │
│  Conversation history      (grows with turns)                    │
│  Current user message      (variable)                            │
│  Tool definitions          (if using function calling)           │
│  Retrieved context         (if using RAG)                        │
│                                                                  │
│  OUTPUT TOKEN SOURCES (charged at output rate, ~3-5x higher)     │
│  ──────────────────────────────────────────────────────          │
│  Model response text       (main answer)                         │
│  Reasoning trace           (if thinking mode enabled)            │
│  Tool call arguments       (if model invokes a tool)             │
└──────────────────────────────────────────────────────────────────┘
```

The things you can control:

| Optimization | Effect | Priority |
|---|---|---|
| Shorten system prompt | Reduces input on every call | High |
| Truncate/summarize history | Caps input growth in long conversations | High |
| Constrain output length in prompt | Reduces output tokens directly | High |
| Disable reasoning mode when not needed | Eliminates reasoning trace tokens | High |
| Reduce tool definitions | Fewer input tokens per call | Medium |
| Smaller context window via RAG precision | Less retrieved text injected | Medium |

Output tokens cost more per token, but input tokens accumulate quietly across the lifetime of a session. Both deserve attention. The difference between a carefully scoped prompt and a loose one is often not quality, it is money.
